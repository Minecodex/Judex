## 为什么这样组织

当前工作区同时承担项目导航、工作图、聊天、交接、审批与设置，用户需要在三栏和多个标签之间理解太多入口。新方案把访问路径固定为：

项目列表 → 项目协同（计划／需要我决定／交付与接收／共享资料）→ 计划任务路线 → 任务详情或具体讨论。

计划、任务卡片主体进入工作结构或详情，右下角“进入讨论”进入 Chatbox；“预览路线”弹窗只复用路线图，不改变当前入口。全局右上角统一账户、语言、主题与退出，项目邀请和项目设置移动到项目卡片；聊天左下角不再放人物与账户菜单。项目内协同页可以再次进入项目设置，避免回到项目列表才能管理。

Chatbox 是按对象进入的讨论视图：计划左栏只显示该计划关联的主讨论、任务讨论和专项讨论；任务左栏只显示该任务的主讨论和相关专项。跨计划不是另一类入口。一场会话有一个稳定 ID、消息历史和决定引用，关联多个计划／任务后，在这些对象的列表中显示同一场会话。关联限定在同一项目，关联聊天不改变任务归属、正式分配、依赖或成果贡献。

| 位置 | 主要操作 | 返回位置 |

独立“待办概览”入口可以取消。但执行工作不能被“需要我决定”替代：demo 已在计划列表提供“我负责”筛选及本人待开展任务提示；正式改造还应在路线图提供本人任务高亮。前置任务仍可见，不能因筛选隐藏依赖。

## 交接和验收如何收敛

“完成任务后等对方同意”可能指两种不同动作，必须在卡片上标明：

- 任务交付：成果已交付，等待 reviewer 对固定成果和完成条件作最终验收。最终状态是任务 accepted。
- 成果交接：某个 sender 将固定报告／材料版本发送给 receiver，receiver 接收后完成交接。接收不替代来源任务的最终验收；需要该 receipt 的后续工作可以解除对应阻塞。

因此使用“交付与接收” tab，而不是继续把“交接信箱”放到聊天左侧。该 tab 包含任务交付卡片和成果交接卡片，提供全部／待我接收／等待对方／需我补充筛选。接收可以同时出现在“需要我决定”中，是同一记录的不同查询视图，不再计一份业务对象。

“需要我决定”不能只按 task.status=delivered 过滤。它必须聚合并显式区分安排审批、任务验收、计划整体验收、交接接收。还没有正式任务的安排提案、负责人对计划的整体验收都要有对应卡片。内容、材料、任职或条件已变化时要求重新审阅，不能把相同名称当作相同版本。

## 讨论创建与本地上报

计划已经拥有稳定 mainTopicId。任务采用 get-or-create 的按需主讨论：第一次点击由成员明确发起创建，以后所有人复用。上报进度、交付或问题本身不创建任务主讨论，也不为每一份报告开会话。

普通进展／交付 → 任务原记录 → 材料 ready 后独立分析 → 当前任务最新摘要。问题 → 通信记录与讨论建议 → 人选择单独讨论、计划主讨论继续或明确已有会话。回复明确带 taskId 和 topicId；关联多个任务时，输入框让用户选择本次发言／上报的任务上下文，不把一份报告平均记入所有关联任务。

计划从讨论形成时仍冻结来源消息点，保留原讨论；一次产生多个计划时分别建分支。手动分叉保留固定公开历史的原消息身份和材料版本，新的 AI 会话、草稿和后续消息独立。多对象关联共享同一会话，分叉则创建新的会话：两种操作的用途和结果不能混淆。

## 业务闭环核对

| 环节 | 必须保留的事实与边界 | 新交互入口 |
| --- | --- | --- |
| 项目与成员 | 账户独立，项目成员与邀请有明确状态，接受前不当作已加入 | 项目卡邀请、项目设置成员 |
| 职位 | 公开职责、具体任职身份、当前绑定；换人承接身份记录 | 项目设置职位职责 |
| 流程 | 已发布节点职责、参与职位、确定的硬条件；AI 不自行改正式绑定 | 设置与任务详情的流程参考 |
| 计划与任务 | 安排先草稿、按职责会签后生效；任务仍只有一个所属计划 | 计划卡、路线图与安排卡 |
| AI 对话推进 | 读当前正式事实及关联公开历史，保存依据、缺口和建议 | 按计划／任务进入的 Chatbox |
| 本地工作与回流 | 实际工作在本地；原报告、作者、来源、固定材料与版本可回溯 | 任务记录与本地 AI 接入 |
| 交付与接收 | 交付、接收、拒收、补交分别记；仅影响对应来源和后续条件 | 交付与接收卡片 |
| 正式审批 | 谁能决定、决定哪版、还缺哪些职责，退回需理由 | 需要我决定与讨论引用卡 |
| 任务验收 | reviewer 明确验收固定贡献与条件，AI／聊天／接收不能代替 | 任务验收卡 |
| 计划完成 | 必需任务满足条件后由 owner 整体验收，历史验收与当前重开分开 | 计划验收卡与状态提示 |

在规则层，这套路径可以闭环，数据对象无需推倒重建。工程上主要是导航、路由、权限查询投影和上下文范围重构，并补充稳定的任务主讨论关系。不能因为 UI 更简单就删除流程约束、审批位、交接来源版本或验收快照。

当前代码的多流程路由仍有独立未关闭项：已有 [职位多流程关联实测](./职位多流程关联实测.md) 明确记录节点判定和任务绑定冲突未全部通过。正式改造时，已定位任务从正式任务／计划取得流程依据；未定位的内容由模型在合法候选中提出关联建议，歧义时只问必要业务事实。聊天所在计划不是强行改绑流程的理由。这个 demo 不代表这些后端实测门槛已解决。

## 个人入口的解释

取消单独的“个人设置”导航和聊天左下角菜单，与保留账户的语言、主题、安全和退出能力不冲突。私有职位工作提示词应放到“项目设置 → 职位与职责 → 本人当前任职”，只对本人显示；公开岗位职责仍与个人偏好分开。demo 将私有编辑放在对应职位内，不把提示词加入公共聊天或交接。
