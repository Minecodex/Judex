# 新版 ToC Demo：三种工作入口

后续反馈：用户认为本页三套交互差异不够，要求先制作 Chatbox 简单草图。当前优先比较 [Chatbox 交互草图](./Chatbox交互草图.md) 中的标签、双栏和主会场 / 侧聊模式；本页继续保留上一轮完整原型的范围记录，不代表用户已选定这些入口。

日期：2026-09-25。状态：已实现可操作的本地前端原型，供选择交互方向；不是生产系统。

用户在确认 Q001～Q055 后要求完善 Demo，并允许在需要重设计时给出多个 ToC 版本。旧原型把工作放在 Topic.work 内，无法清楚表达独立计划、任务和逐来源交接，因此本轮重排业务模型与入口。此前删除的 Orbit/Focus 页面没有恢复；这是围绕新模型重新设计的三套入口。

## 1. 三套方案

| 方案 | 入口 | 主要交互 | 适合观察的问题 |
| --- | --- | --- | --- |
| 灵感工作室 2.0 | 打开（历史地址：`http://127.0.0.1:4173/?design=studio`） | 项目与阶段计划卡片 → 任务树与详情 → 交付、交接、验收 | 日常工作是否自然，能否同时看清阶段目标和待办 |
| 协作信箱 | 打开（历史地址：`http://127.0.0.1:4173/?design=mail`） | 收件分类 → 交接摘要 → 来源级接收/拒收 → 回到任务 | 能否用较少导航完成接收与补交，清楚看见是谁交给谁 |
| 计划地图 | 打开（历史地址：`http://127.0.0.1:4173/?design=map`） | 重点交接路径 → 任务节点 → 侧边详情 → 负责人整体验收 | 多人工作关系与前置条件是否容易理解 |

顶部切换三个入口，业务记录不重置。单独打开多个标签页也会通过浏览器存储事件同步这份示例；这不等于服务端并发事务。语言、深浅色及演示身份均可切换。

设计建议：以工作室承载日常项目体验，信箱适合处理交接，地图适合检查计划关系。三者也可分别作为候选主入口评审，尚未替用户选定唯一新版。

## 2. 共用的数据与操作

新模型在 src/work 中独立实现，包含项目、职位模板、稳定任职身份、计划、任务、流程、交接及其来源、议题和操作事件。不同页面引用同一对象；议题关闭不改变任务或计划进度。

已能操作：

- 计划列表、负责人和整体验收条件、所属任务树、条件与引用展示；创建计划/任务草稿及相应有权人确认。
- 项目直属临时任务；示例中的跨计划成果引用不复制任务，也不计入引用方的所属任务数。
- 本人工作上报、附件与原件查看、本地简报、任务最终验收；任务重开保留事件历史，计划状态由负责人明确更新。
- 同任务换环节与跨任务交接草稿；目标限定在已有工作关联身份内，各来源必须本人确认发送。
- 多来源分别接收或带原因拒收、补交新版本、重新确认发送；未变化来源保留接收。
- 硬条件示例：接收指定来源才可开始下一项工作，提交本任务验证依据才可最终验收。开始条件与产出验收条件分开，避免让任务必须先产出成果才能开始。
- 独立议题可关联多个计划和任务，支持普通文字与附件；聊天中的“同意/完成”不构成正式批准。
- 职位模板创建、提示词与具体流程节点挂载；同岗多人、邀请后多职位任职、替换关联人、本人项目提示词与查看范围。
- 实际 Mermaid 图渲染；示例流程草稿编辑与人工发布，后续简报使用新版。由管理者明确标记本次变更影响待接收内容时，相关卡片需重核、各受影响来源重新确认发送。
- 任务验收窗口绑定已展示的工作版本，计划验收绑定其所审任务依据；打开窗口后有新上报时不能用旧窗口批准新内容。

演示身份：

| 人员 | 示例职责 |
| --- | --- |
| 周宁（默认） | 接收两份交付、逐项拒收或接收、整理体验包；也是“野间咖啡”示例负责人 |
| 顾言 | “实现伙伴”任职身份，提交与发送功能交付 |
| 江澄 | 同一个“实现伙伴”模板下的另一份任职身份 |
| 夏禾 | “内容伙伴”，可补交被退回的使用说明 |
| 林然 | 示例计划负责人、整体验收及工作安排确认人 |
| 沈言 | 项目管理者，可维护职位和流程，不因管理身份自动取得任务或计划验收权 |
| 赵可 | 尚待接受“实现伙伴＋内容伙伴”职位邀请 |

这些职责是示例数据及其授权，岗位名字和模板可修改，不是平台固定的开发/测试角色。

## 3. 推荐体验路径

1. 默认以周宁打开协作信箱，接受顾言的交付，拒收夏禾的说明并填写原因。
2. 切换夏禾，进入交接记录，只补交说明与附件，再明确确认发送。
3. 切回周宁，接收新版本；顾言原来的接收结果保持不变。
4. 打开“整理首版体验与交付包”，检查明确硬条件、开始工作并上报成果。
5. 切换林然进行任务最终验收；只有本计划所属工作满足示例约定后，才能确认计划整体验收。
6. 重新打开一个已验收任务，观察计划的复核提醒与保留的正式状态。
7. 切换沈言，在流程页生成示例修改并发布，勾选对待接收要求有影响，观察旧卡重新核对与独立发送确认。
8. 切换赵可接受职位邀请，配置个人偏好；管理者查看该身份时不会在提示词预览中看到其私人偏好。

同一组操作可在三种入口之间切换继续，不需要分别维护三份计划或数据。

## 4. 已实现与模拟边界

这是浏览器本地原型，没有真实 Agent、业务后端、生产鉴权或 CLI/API。AI 回复、进度说明和“按描述整理流程”使用可编辑示例，未调用真实模型。流程图由明确节点/边生成；新增流程演示使用用户可编辑的顺序节点，未实现任意自然语言流程编译。

任务硬条件验证是真实前端逻辑，但当前展示的是已结构化的示例条件，没有宣称模型能自动把任何文字转为强校验。流程改版影响由管理者在演示中明确标记，不是自动语义差异分析。

示例采用单个被明确指定的工作安排确认人/任务验收身份；完整可配置多人会签仍保留在旧版供参考，尚未迁入新工作草稿模型。身份切换用于体验，资料与个人提示词均保存在同一浏览器，不能作为生产隐私隔离。

提醒按钮只记录一次模拟提醒，不启动后台定时任务，不远程唤醒成员本地 AI。任务树及引用可查看，尚无拖拽重组或完整的依赖编辑器。流程地图突出示例中的交接路径，实际任务条件还可在计划依赖视图和任务详情核对。

附件每个最多 1 MB，文本/图片可预览，其它文件保留原件。所有内置代码、验证报告和场景均为虚构；不会创建 Git 分支、部署服务器或发布代码。
