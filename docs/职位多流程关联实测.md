# 职位多流程关联与未显式指定流程的真实模型实测

日期：2026-10-07。目的：验证一个职位关联多个项目流程节点后，CLI 上报不提供 workflowId/nodeId 时，平台和真实模型分别能做到什么。本文记录实验与候选方案，不提前确立无条件自动路由规则。

## 实验边界

- 使用现有部署配置中的 GLM-5.3，真实网络调用；没有受控模型、关键字路由或预置回答。密钥只在进程环境和本轮所属 namespace Secret 中使用。
- 在隔离 namespace 建立一个项目、一名测试成员、一个工程协作职位。该职位关联三条已发布流程的六个节点；不同流程刻意使用同样的 work/verify 节点 ID。
- 三条流程分别定义软件功能交付、线上事故处理、性能优化验证，说明适用背景、排除条件及节点职责。职位关联不增加审批和验收权。
- CLI 实际构建并运行；报告正文与 JSON 均不显式选择流程或节点。任务 ID 与任职身份属于已有正式工作定位，需要与“模型从内容推断流程”区分。
- 正式审批只用于本轮测试项目的合成安排。既有运行部署、业务数据及真实用户决定不修改；测试结束核对 namespace UID/标签后清理。

## 两种证据分别评估

**现有平台链路**通过真实注册、项目/流程/职位 API、任职、工作安排、CLI 报告/资料上传、真实模型和 PostgreSQL 分析记录验证。任务本身已有流程节点时，平台可以沿用该安排，不能将这种情况算作模型自动发现流程。

**模型判定能力实验**读取上述实际保存的流程、节点及职位关联，给同一真实模型提供完整候选背景。12 类案例各使用两种自然表达，第二轮反转流程顺序，共 24 次独立调用。答案和案例标签不发送给模型。只读的 record_workflow_routing 是实验工具，不是已接入平台的业务接口，不写任务绑定或触发正式变更。

预先登记的严格标准要求匹配“本次事项当前对应的流程与节点”；背景不足应返回澄清，无适用候选应保持未关联，既有任务关联与内容冲突时应先核对。全部原始输出、预期、调用 ID、使用量和耗时保留，失败不改成通过。

## 模型判定结果

首轮统一输出预算 4096 tokens，24 次中严格通过 16 次、未通过 8 次。

| 验证内容 | 结果 | 含义 |
| --- | --- | --- |
| 明确信息下的流程集合，包括跨流程事项 | 16/16 对应正确 | 本组样本支持不要求用户填写流程 ID；不代表所有实际项目均达到相同准确率 |
| 上述事项的严格当前节点集合 | 11/16 对应一致 | 另 5 次多选同流程中的前序或后续节点，未选错另一条流程 |
| 无背景的模糊内容 | 2/2 请求澄清 | 能保留不确定性，不强行猜测 |
| 事故/性能场景重叠的内容 | 1/2 请求澄清 | 另一次输出达到 4096 tokens，未返回结构化工具结果 |
| 上报与任务既有关联冲突 | 0/2 按标准请求澄清 | 两次都按新内容选择事故流程，未执行任务绑定修改，但没有按实验要求先核对归属 |
| 无适用流程的内容 | 2/2 保持未关联 | 招聘/活动事项没有被塞进工程流程 |

针对场景重叠和任务关联冲突，保持同一提示词、同一候选配置和预期，仅将输出预算提高至 8192 tokens，另做 4 次复测：重叠案例 2/2 正确请求澄清；任务关联冲突仍为 0/2。原 24 次记录不替换，复测独立保存。

需要解释“多选节点”的口径：例如报告既说功能实现完成，又指出跨浏览器证据未补齐，模型将实现与证据核对都视为相关节点；事故复盘报告也可能同时引用先前恢复环节。这作为流程参考有合理性，但不能将所有相关节点直接视为本次要触发的环节。必须先区分当前事项、历史依据与后续建议。

## 当前源码的 CLI 链路

使用当前工作区源码构建的镜像，与原部署共用相同的真实模型配置。5 个事项通过实际 CLI 上报，其中性能事项附带实际上传、固定版本的 UTF-8 文本材料。所有报告都省略 workflowId/nodeId。

| 事项及已有背景 | 观察结果 | 能证明什么 |
| --- | --- | --- |
| 软件交付任务已有流程与 work 节点 | completed | 沿用正式工作关联，真实岗位核对与结构化公开分析完成 |
| 事故任务已有流程与 work 节点 | waiting_human | 中间公开分析正确说明事故恢复环节，但岗位调用出现不适用工具错误，整轮未完成 |
| 性能任务已有流程与 verify 节点，附实际上传材料 | completed | 读取了固定材料版本，完成公开分析并保留缺口 |
| 计划已有关联流程，任务没有 workflowId/nodeId | 300 秒观察窗口内仍为 running | 协调者与岗位上下文的 workflowVersions 均为空；未验证出对应流程/节点的闭环 |
| 任务和计划均无流程关联，正文明确描述生产故障 | 300 秒观察窗口内仍为 running | 项目确有三条流程与六条职位关联，但两层上下文均没有候选流程，未形成完整分析结果 |
| 自由 submit 不带 taskId/topicId | ready，原内容保存；没有对应分析批次 | 当前入口没有将未关联内容自动分类并进入任务分析 |

两个观察窗口结束后保存证据并清理所属环境；不将仍在运行的批次说成永久失败，也不将其计为已完成。CLI 上报已经保存，已上报任务保持 working，已有流程/节点关联未被模型改写。职位卡片的六条关联显示断言及实际截图通过。

平台调用与纯模型判定分别留证：当前源码两个隔离实验共登记 45 条 model_calls，其中 43 条记录为 succeeded、2 条在截取证据时仍为 running；这些数量不能换算为 45 次完整业务闭环。

发现的具体缺口：

- 任务分析的候选流程查询只取 tasks.workflow_id。任务未绑定时即使计划有关联、职位关联了六个节点，也未将这些候选交给模型。角色目录也未带出职位节点关联。应先解决平台提供的背景不全，再判断用户定义是否有歧义。
- 岗位运行仍能看到 record_task_analysis 工具，但保存入口只允许协调者。本次复现 FORBIDDEN，事故批次出现岗位结果 unknown 后进入 waiting_human；无流程任务中也出现相同工具错误。真实权限校验生效，工具暴露与恢复契约仍需完善。
- 平台的 TaskAnalysis 目前只保存 summary/basis/disagreements/讨论建议，没有独立的流程节点判定结果契约。文字里提及某流程或建议下一步不能视为节点已被正式触发。
- 初始长测试使用一次性 JUDEX_TOKEN，在 15 分钟后过期，导致第五份报告未发出。已为各测试命令组重新授权并仅补跑该事项及自由提交，原失败保留。这是测试认证方式的问题，不计为模型无法识别。
- 对无 --task 的 report 另行执行了实际 CLI 缺参检查：退出码为 0、没有输出。命令没有形成报告，但该退出结果会误导宿主；不能将 JSON 解析异常当成已经验证 CLI 正确拒绝。实验现已记录真实进程退出码，并把该情况作为独立失败项。

三次隔离 namespace 均已按所属检查后删除；各次前后核对原 judex 部署 UID、generation、镜像及 7 类业务表计数一致。本轮没有发布新生产逻辑，也没有替用户作出真实业务审批。

## 对产品规则的影响

模型在明确背景下可以识别适用流程；多个流程关联到一个职位本身没有表现出必须让用户手动选流程的障碍。但是本次严格节点判定和任务关联冲突没有全部通过，不能据此宣称“平台总能自动判定并触发全部节点”。

可继续验证的方案是：

1. 已定位正式任务时，从该任务及计划取得已有流程依据。新内容与已有安排冲突时记录归属问题，避免悄悄切换正式绑定。
2. 尚未定位流程时，平台提供本项目已发布流程及当前任职职位关联的完整候选；结合计划、任务、正文和固定材料进行判断。不要要求用户预先填写流程/节点 UUID。
3. 将当前事项对应节点、引用的历史/相关节点和建议后续节点分别表达。同一身份参与多个相关节点时合并调用，不复制工作或自动建立多条正式安排。
4. 明确内容自动形成分析与关联建议；重叠或冲突时询问最少必要业务事实，例如“这是生产用户故障，还是隔离环境压测？”。无法判定不自动归咎流程配置错误。
5. 代码校验候选节点存在、项目归属、当前任职及既有工作关联；模型的文字判断不覆盖业务授权或人的验收。模型输出不完整时保留原记录与可解释状态。

这些是后续实现与复测候选。本轮只增加实验、证据和文档，未实施新的生产路由器或改造职位编辑界面。
