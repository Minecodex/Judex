## 1. 总体安排

建立 3 个测试平台项目和对应的 3 个 Kimi 本地项目。预定 8 条工作流程、11 个职位模板、12 份初始任职身份、9 个计划、30 个正式任务样本。初始化、异常注入和缓存对照不另建占位任务。

Kimi 创建 12 个业务会话，另加 2 个专项对照会话，累计 14 个。首阶段软件项目为 6 个业务会话；缓存与接岗阶段再建 2 个对照。用户已批准直接使用公开 `kimi` CLI 和明确会话 ID，实际已验证最多 4 个独立会话并行；不再依赖桌面点击。平台协调者与职位运行不计入 Kimi 会话数量；本轮为K3，历史GLM记录保留。

## 5. 每个场景必须完成的往返

软件首版、图片设计和 Office 报告至少各跑一次完整退回 / 修改：

1. 负责人通过真实会话提出目标，平台模型形成流程 / 工作草稿；编辑、发布与工作安排经测试用户确认。首次建项目走 CLI 意图和浏览器确认，平台项目内 Agent 不被假定具有全局建项目工具。
2. 各成员手动调用 Skill 取得工作，在本地软件制作并保留实际运行 / 打开 / 重算 / 渲染证据。
3. CLI 登记固定材料版本、进度及交付；平台真实模型读取来源，给出职位意见和公开分析。
4. 接收人逐来源确认接收或给理由拒收；实际发现的质量缺口退回修改。使用预登记的测试缺口时，输入及评判依据分离，保留未通过的原结果。
5. 当前任职人使用原会话获取退回事项；已接岗则由 KX02 接续原 identity。修正、重新上报新版本；未受影响来源的接收事实保持，旧审阅对实质变化明确失效。
6. 明确指定的 reviewer 验收任务；该计划 owner 对照整体条件再确认计划。模型运行完成、上传成功和交付接收分别核对，不作为验收的替代。

实际软件由 Kimi / 成员本地工作产生，平台模型分析和提建议。当前用户指定APIMart `glm-5.3-flash` / high，历史K3与Coding Plan证据保留，没有自动额度降级。图片原件生成、图片理解、Office 原件解析及公式重算分别留证；缺少某能力时该项标为未执行或受阻，不以格式预览覆盖。

## 7. 执行次序及准入

1. 先验证软件准入：目标平台模型可用、职位多关联保存、候选上下文、工具权限、同版本 CLI / Skill；探测 Kimi 桌面建项目 / 会话与实际调用。流程建稿能力没有接通时，已有草稿的人工创建可作为局部对照，模型建稿项仍保留缺口。
2. 建 A 的 KA01～KA06，先执行 A-P1；再执行 A-P2 / P3 / P4，期间建立 KX01 作缓存对照。软件阶段优先保持初始测试甲 / 乙身份，接岗留到综合交付待办出现后。
3. 图片工具链具备实际调用能力后建立 B 的 3 个会话，执行 B-P1 / P2；Office 软件及沙箱原件解析具备能力后建立 C 的 3 个会话，执行 C-P1 / P2。
4. 执行 A-P5，在测试甲已有待办 / 未提交意图时建立 KX02 并替换绑定；该身份此后由 KX02 办理，其余角色复用原会话。覆盖综合交付、部分拒收、受影响版本返工及最终计划验收。各阶段同时采集真实缓存计数，结束检查临时 namespace、目录、授权和 TTL 范围。

所有业务对象使用所属隔离 namespace 和独立本地目录，不操作正常项目的正式决定。用户已批准执行；Kimi与平台模型的实际调用、失败和当前阻塞见最新记录。清单仍是验收目标，不能把它当成已通过的测试报告。
