## 长会话诊断与原会话续作

原 KX01 会话不重建、不手工编辑历史。回看原生 wire 后确认：旧 32768 用例确实完成过压缩，但保留用户历史的压缩结果仍约 45000 token，超过人为缩小后的窗口；正常请求因剩余空间不足实际只发送 `max_tokens=1`。因此旧失败不能概括成“压缩从未发生”，增大输出上限本身也不足以解决。

本轮 32768/16384 的再次实测保留失败：20 次真实 high HTTP200，其中10次压缩输出16384、10次正文输出被客户端压为1，没有工具执行。新预检读取最近原生压缩的数字指标，窗口容不下已有上下文和输出预留时，在调用供方前返回 exit2；负控制实际供方调用为0。它不删除历史，也不把不兼容窗口记为成功。

65536/16384 对照沿用同一会话，真实完成2次压缩（45291→45159、48464→44777），随后7次工具执行、CLI exit0；9次供方请求均 high。继续读取新流程的回合也成功结束，47次真实 high 请求、39次工具调用；临时证据文件路径与 JSON 壳提取错误的纠正过程保留。只对这些声明窗口及原会话作结论，不承诺任意小窗口或任意压缩组合。
