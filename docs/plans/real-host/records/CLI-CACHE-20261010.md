# CLI 可靠性与 24 小时缓存观测最小版

更新：2026-10-10。范围：前置方案中的 CLI 可靠性和平台缓存观测；流程候选、岗位权限、流程建稿、Office 与图片分析仍是后续阶段。

当前源码已完成实现。缓存与 CLI 的隔离验证、发行构建和真实 Kimi 错误识别分别记录，不能将受控网关的缓存数字当作真实 GLM 命中。

## 实现

- CLI 增加统一 Run 入口：Cobra 解析 / 必填参数错误、业务错误均有输出和正确退出码；参数错误为 2，认证 / 权限 / 冲突 / 网络等保持约定分类。JSON 模式 stdout 只有一个结果，业务已经输出的部分成功信息不会被覆盖或重复打印。
- OpenAI-compatible / Anthropic-compatible Provider 使用完整 UsageSnapshot，区分 null 与明确 0，保留累计计数、模型及请求 ID。Runner 不再把明细折叠成一个总数，累计 usage 帧不重复相加；未完成流不冒充成功调用。
- 工具 schema 名称排序，同次请求复用同一份 schema；OpenAI 工具回传按模型提供的 index 排序。
- 规范化明细存入既有 model_calls.usage_json.observation。无新观测表；迁移 27 只增加到期部分索引。
- 从调用 ended_at 起滚动保留 24 小时。[查询](../cache-observation.sql)到期立即排除；worker 启动即清理，然后每分钟清理。每批最多 500 条，一轮最多 16 批，SKIP LOCKED 允许多 worker 共存。
- 过期只清除 observation 与供应商请求 ID。原 model_calls 行、调用序号、请求摘要、预留、总 token 和 usage_known 保留，恢复与预算不会因为观测过期而倒退。
- 维护协程沿用 worker 生命周期；不生成持续积累的定时任务记录。停机期间过期的明细在 worker 启动首轮清理，逻辑查询一直以 24 小时截止。
