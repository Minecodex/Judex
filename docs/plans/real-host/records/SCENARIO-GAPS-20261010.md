S10 的基础设施故障、S06 的权限 / 确认和 S09 的材料版本均已有部分自动化专项覆盖；尚缺的是它们在真实宿主制作与返工中的共同证据。S13 的到期查询、worker 启动及周期清理已经用 25 小时的记录测试通过；自然跨日与大量到期积压属于持续运行补测，不能把 TTL 基础功能重新标为未测。

Codex / Claude Code 等其他 AI 宿主属于扩展项：历史安装 / 发现证据不能代替真实模型执行。原始范围优先完成 Kimi，其他宿主按明确的目标版本和工具范围逐项增加。

## 4. 实际执行顺序与证据要求

1. 关闭软件场景的 P0：平台模型配置、多关联编辑、候选上下文和工具权限；按 S01 / S03 / S06 跑一个已明确安排的软件项目完整往返。流程建稿与自由提交按 S02 / S05 独立验收。
2. 扩展到第二项目和并行职位 / 会话，覆盖冲突、交接、拒绝和恢复（S04 / S05 / S10 / S11）。
3. 补齐图片与 Office 工具链后分别执行 S07 / S08，再合并为 S09；每个阶段同步执行 S12 缓存观测。
4. 对同一发行制品执行 S13，记录持续运行限制，再决定正式部署验收是否关闭。

每个场景预先记录项目、用户、授权、职位、会话、模型、流程版本、预期业务状态和失败条件；使用所属临时 namespace、独立本地目录及凭据配置。结果保留脱敏宿主轨迹、CLI 退出码 / JSON、真实模型调用及工具结果、材料 versionId / SHA、实际软件打开 / 运行证据、Web 确认与数据库正式事实。只读查询或截图不能独自代替业务断言。

平台缓存明细继续只保留滚动 24 小时。测试过程中及时计算脱敏汇总和样本计数；长期证据不复制逐调用缓存明细、供应商请求 ID、原提示词或凭据。首次调用也不保证供应商全局冷缓存，未返回缓存计数不当成 0，不预设固定高命中率门槛，不为缓存命中省略必要的最新业务 / 权限背景。

全套业务门槛继续对照 [V1 测试与验收](../../v1/10-测试与验收.md) 的 D / E / F / G 条目。本记录是覆盖审计与探测清单，不是综合测试通过报告。
