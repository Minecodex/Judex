# 03 工作、审批与交接

## 1. 领域不变量

任务最多一个 owning plan，可直属项目；同项目可跨计划引用，不复制任务进度。parentTaskId 表示拆分，requirements 表示先后，两者分开检测环。关联父子必须同项目、同 owning plan；移动范围属于提案。

正式业务决定不来自聊天文字、AI run 成功、文件上传成功或 Git push。项目管理能力不自动包含任务验收权；实际 actor、代表身份和权限来源分别审计。

## 2. 状态迁移及角色

| 对象／命令 | 从 → 到 | 必须主体和条件 |
| --- | --- | --- |
| 计划 draft | 无 → draft | 项目成员创建草稿，AI/CLI 可准备 |
| 计划生效 | draft → active | 正式工作安排提案满足审批；owner identity、目标、条件完整 |
| 计划验收 | active → accepted | 当前计划 owner 绑定人，任务及引用成果条件满足，核验 snapshot |
| 计划重开 | accepted → active | 计划 owner 明确理由，保留旧 acceptance；不是子任务自动触发 |
| 任务生效 | draft → ready | 工作安排提案生效，身份／节点／条件有效 |
| 开始任务 | ready/rework → working | 当前 task participant，满足 start/both 硬条件 |
| 进度上报 | working/rework 保持 | 当前责任人或其受限 CLI，report_kind=progress；进度是提示不是验收 |
| 成果上报 | ready/working/rework → delivered | 当前责任人，start 硬条件满足，ready 材料清单完整，kind=delivery |
| 任务验收 | delivered → accepted | 当前 reviewer，accept/both 硬条件满足、对应 report/evidence 未变化 |
| 验收退回 | delivered → rework | 当前 reviewer，必须理由，旧报告保留 |
| 任务重开 | accepted → rework | 当前 reviewer 明确理由和引用原 acceptance；新范围另建任务 |
| 提案提交 | draft → pending | 本次指定 sender/有权代表人确认，冻结 payload、名单和 manifest |
| 提案通过 | pending → approved | 所有审批位满足，当前约束有效，原子应用全部变更 |
| 提案退回 | pending → cancelled | 任一当前审批人给理由；reason=rejected，停止其他待批与 timeout |
| 提案过期依据 | pending → stale | 相关 manifest 硬依赖已失效；需新版本重收，不继承旧票 |
| 来源发送 | draft/revised → pending | 该来源当前 sender，固定 sourceVersion/report/接收人 |
| 来源接收 | pending → accepted | 当前 receiver，明确 receipt，不隐式验收来源任务 |
| 来源拒收 | pending → rejected | 当前 receiver＋理由，仅影响该来源相关后续 |

已 accepted 任务不能由迟到 report/进度自动降级；返回 INVALID_TRANSITION，须 reviewer 重开。重复上报用幂等返回原报告。过时事件不覆盖新状态。

V1 补充工程规则：未完成计划/任务可以通过 work_change 提案取消，进入 cancelled，记录理由和对依赖/范围的影响；不能由普通 PATCH 或 AI 自行取消。取消项不计作完成，后继依赖保持阻塞直到另一个已批准变更调整条件。计划取消不抹掉子任务既有验收；已 accepted 对象不允许直接改 cancelled。草稿丢弃可由作者执行，但仍不删除已被引用版本。任务枚举增加 cancelled，前端按“取消”单列，禁止把它映射成 accepted。

任务多参与者可以各自上报，但提交整任务 delivery 必须引用当前所有约定必需贡献；该清单来自正式 task agreement，不取“最新一人的内容”。当前前端单 reviewer 设计保留，多 reviewer 验收用独立正式提案表达，不悄悄只验第一个。

## 3. 通用提案与自动应用

提案 kind：work_arrangement、work_change、dependency_change、material_link、topic_creation、formal_conclusion、handoff_change、release_acceptance。payload 用版本化判别联合，不接受任意 table/field 的通用 PATCH。

`changes[]` 每项至少：operation、targetType、targetId/clientRef、expectedVersion（新对象省略）、fields、dependsOn。允许操作白名单 create_plan/create_task/update_scope/set_assignment/set_requirements/link_material/link_topic 等。新对象之间用 clientRef，服务端一次性分配真实 ID，返回 createdIds 映射。

提案提交前服务器计算收件和审批资格：AI 可建议人选，服务端保证流程强制节点、受影响职责和必要人员不遗漏；发送人看到最终名单和变化清单再提交。责任 slot 按稳定 identity 或明确 user 授权定义，同一真人当前持有多个 slot 时合为一次明确同意、记录一份覆盖多个 slot 的 decision；UI 真人数按 userId 去重，不把兼岗当成多个真人。owner/manager 不能任意移除必须审批的反对者。

正式提交冻结：文字/报告、changes、稳定责任 identity/user slots、提交时接收人及 bindingVersions 快照、timeout policy、workflow constraint hashes、目标版本、材料版本、依赖决定。`reviewHash=SHA256(canonical JSON)`；前端提交 reviewId/hash，服务端重新校验。提交时人员快照保留用于审计，当前办理人从稳定身份绑定另行计算；绑定变化不改报告内容hash，但该次确认的actingBindingVersion必须是当前值。新增无关聊天不让所有审批失效。

所有票满足后，在同一 project 事务内验证依赖→应用整组 changes→写 accepted decision 和新工作→event/outbox。一处失败整体不应用，返回明确冲突并标 stale，不留下“批准了但只建了一半任务”。后续 AI 分析失败不能撤销已提交的业务事务。

不同问题拆成多个 proposals，可用 bundleId 展示；部分采纳按 proposal 为单位。跨提案依赖必须引用 approved 上游及版本，不能执行一个依赖尚未成立的子集。

## 4. 首票计时、超时和代批

- 工程默认 24 自然小时，项目默认可调、节点可覆盖；提交时冻结秒数，之后改配置不追溯旧提案。
- 首次有效人工同意（含显式合法代批）设置 firstApprovalAt、deadlineAt 并持久入队。后续同意不重置；从未有人同意则无超时自动通过。
- 到期 worker 锁 project→proposal→slots，核验 pending、deadline 与完整 reviewManifest；仍有效才为未回应 slot 记录 timeout，同事务尝试最终应用。timeout actor 不是该真人。
- 任何退回在 pending 期间取消整提案；race 按获得锁并核验状态的顺序唯一生效。截止已过但 worker 尚未处理时，人工请求进入同一命令函数先结算到期规则，再给出最终状态。批准后不再提供旧拒绝按钮；新异议创建修订/重开事项。
- 同一 slot 已生效的票不可撤回；要改变结论提交新提案。此为 V1 工程规则，UI 明示。
- 代批需具备该节点的 delegation authority 或该项目明确指定负责人权限；请求列明 slotIds 和理由，只覆盖 pending 位，不覆盖 reject，不能伪装原人亲批。服务端记录 actor＋delegatedFor。
- 无回应交接只提醒，永不复用 approval timeout handler 自动接收。

## 5. 换人、改流程与旧决定

已成立决定保留原 actual user 与 bindingVersion；换人不抹去历史同意/反对。不再接受旧绑定持有者的新决定或工具调用。

待决 review 的内容和责任席位被冻结。按最新 V2-Q028/Q038，身份更换绑定后，pending职责由新绑定人直接接续；原deadline、首票时间、已成立决定和退回保持，不新增换人交接审批、不整体重收同意。原人的未提交浏览器/CLI确认意图因bindingVersion过期而失效，新人获取相同review及当前资格重新发起自己的操作。

已经同意的职责不因换人变回pending；新绑定人不同意历史结论应发起新的变更提议。若同一真人原已为身份A投票，后来又承接pending身份B，旧票不能自动覆盖B；需对新增职责明确确认，UI仍按真人去重显示而非多计票。涉及明确user而非岗位的slot不因任职替换转给别人。

审批过程中仅换绑定不修改slots集合；真正增删责任、内容/依赖变化才需要新review并重收同意。已存在的reject不因换人消失，cancelled提案不能复活。前端演示 `proposalIsCurrent` 将binding变化一律判失效只是预览实现，应在生产接入时替换。

流程新版每次后续模型调用获取。仅与 reviewManifest 相关的职责/节点/硬条件变化触发 stale；无关变更只显示新参考版本。影响不明确时人工核对影响范围，不由 AI 一句话跨过版本校验。

## 6. 交接与补交

handoff 包含多个 source，各自指向来源任务、sender identity、固定 report/version。可跨任务交接，也可同任务不同阶段交接。每个 sender 只确认自己的 source；receiver 对每个 source 分别 accept/reject，可批量审阅但提交列明版本集合。

拒收未最终验收任务的贡献，将该相关任务标 rework，阻塞依赖该 receipt 的后续；其他 source 接受结果保留。来源任务已经 accepted 时，拒收仅提出重开请求并提醒 reviewer，不能由普通 receiver 越权撤销最终验收。

补交创建新 source_version，保留旧 source decision；发送人重新确认。只清除新来源的待收状态。若声明影响其他来源，由受影响发送人确认修订后再交接；未声明但结构化依赖发现变化时阻止沿用过期接收。

整包状态计算：全部 required sources accepted→accepted；有 rejected→needs_revision；其余 pending/draft→waiting。计算整包不把源任务都标 accepted，也不自动给下游填工作报告。

## 7. 验收快照与计划聚合

任务验收 manifest 包含 task agreement version、当前 contributions/reportIds、materials versions、硬条件结果及身份 bindingVersion。弹窗展示“验收的是哪份成果”；提交时快照不一致返回 REVIEW_STALE 和需要重读的对象列表。

计划整体验收引用各任务 acceptanceId、referenceTaskIds 和阶段目标。任务全部验收只产生可操作待办；计划 owner 仍需确认。已有 accepted 计划内任务重开时显示“历史已验收／当前存在重开工作”，提醒 owner；不能以历史 accepted 隐藏当下问题。

聚合可返回 counts、completionHint、blockers、reopenedAfterAcceptance。进度按任务有效验收计数，AI 分析百分比单独字段，禁止前端二者混算。

## 8. Bug、仓库和环境上报

Bug 使用 task.kind=bug＋bug_details，含复现步骤、预期/实际、严重程度、图片及原任务/版本。测试人员创建 Bug 草稿，关联已 accepted 任务时提出 re-open，不自动越权改变已验收结论；计划内新 Bug 形成正式任务仍走工作安排。

repository_links 保存 Git 地址及主分支名字，report 的 codeRefs 包含 repositoryId、branch、commit SHA、PR URL、用户说明。平台仅检查结构与关联，未经真实验证的引用标 reported，不能伪称已 merge。外部仓库自动采集是可选适配，首版不要求 GitHub App 才能工作。

release_report 保存环境、URL、各仓库准确 commit、实际执行人和结果。运维本地部署后 Web/CLI 上报；失败上报产生待办，不自动重部署。版本命名可用 semver 但不强制 feature/release/bugfix，避免复活旧 V1 执行约束。

修复传播目标由用户选择，创建独立 fix_propagation 与目标任务；源任务按源版本验收，其他目标可进行中/部分失败。总览不能把源完成显示为所有版本完成。

## 9. 必测竞态

最后同意 vs 退回；timeout vs 人工决定；相同幂等键重试；两个不同 payload 同键；审批 vs 任务新报告；绑定替换 vs CLI 意图确认；依赖边 A→B 与 B→A 并发写入；验收 vs 重开；两个来源独立补交；全部任务验收 vs 新增正式任务。每例必须在真实 PG 多连接测试，不能只测单线程纯函数。
