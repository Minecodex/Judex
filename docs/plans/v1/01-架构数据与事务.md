# 01 架构、数据与事务

## 1. 模块和依赖

保留 `cmd/judex-server`／`cmd/judex`。入口只做装配和退出码。HTTP handler → application service → domain policy → repository；领域层不引用 Gin，不做网络请求，不读取前端状态。后台任务通过同一应用服务执行。

建议新增：`internal/platform/{database,clock,idempotency,events,errors}` 提供低层设施；`internal/infrastructure/{postgres,s3,opensandbox,model}` 实现适配；领域按现有 identity/project/work/decision/handoff/discussion/material/workflow/agent/job/audit 分包。CLI 放 `internal/cli`，共享 HTTP client 放 `pkg/client`；仅在契约冻结后确定可公开 Go SDK 的稳定性。

跨模块事务由用例层持有 `Tx`，依赖窄接口，不让 decision 直接拼 SQL 修改所有模块。`decision.ApplyProposal` 调用 work、handoff 等同事务的应用方法。读模型可跨表联查，但不能由读模型写状态。

API 和 worker 可先在同一进程；支持 `--mode=all|api|worker|migrate` 使用同镜像。任务持久化使扩 worker 不改变业务协议。外部网络调用均在短数据库事务之外。

## 2. 存储和 ID 规则

- PostgreSQL 是唯一正式事实与运行上下文源；不新增 SQLite，不把 WorkState JSON 整体存成一行。
- S3 保存不可变原件和大型产物；沙箱工作目录可丢弃，已登记产物不得只留 Pod。
- SQL ID 用 uuid，业务版本 bigint ≥1，时间 timestamptz；API ID 字符串、版本整数、时间 UTC RFC3339。
- 下表 `P` 表示必须有 project_id；可变对象共同具有 id/version/created_at/updated_at。不可变版本和事件只追加，修改通过新记录。
- 项目内引用使用复合 FK `(project_id, target_id)` 对应唯一键，防止只传一个合法外项目 ID 就越权。普通删除默认 RESTRICT，明确的临时上传清理例外。
- 用户内容是单一 UTF-8 字符串，不能照搬演示 `{zh,en}`。UI 翻译由 i18n 处理；业务原文不自动翻译覆盖。

## 4. 一次正式命令的事务模板

1. 解析真实 Principal；用户相关命令锁 user 行 `FOR SHARE` 核验 active/auth_version；不得信请求中的 userId。随后按固定顺序锁 project 行 `FOR UPDATE`。
2. 再查 membership、identity binding、权限和项目归档状态；非成员响应统一 404。锁目标聚合对象，再按 ID 排序锁关联对象。
3. 读取幂等记录；同键不同载荷返回 409，同键相同且已完成返回原结果（返回前仍检查当前访问资格）。不存在则本事务插入。
4. 验 expectedVersion/reviewHash、状态、硬前置、固定审阅清单和当前身份；执行纯领域校验。
5. 更新业务状态与 version，写审计，递增 projects.event_seq，写 project_events/outbox/jobs。命令返回所有受影响资源 ID/版本。
6. 幂等结果与业务同事务提交；提交后才响应成功。请求断连不意味着回滚已经提交的事务。外部模型／S3／沙箱不得放入这个锁窗口。

同项目 guard 还保护依赖环检查、最后 owner、审批与 timeout 竞争及事件顺序；不能部分 handler 忘记锁而破坏整体约束。用户停用先锁 user 排他，撤销 auth_version 后再由项目任务清理运行；与正式命令的 user→project 顺序一致。

幂等请求哈希覆盖 method、规范化 route、body、版本、主体和 scope；文件内容以已验 SHA 引用。默认保留 30 天（配置项）；正式决定还有 review/slot 唯一约束，幂等记录清理后也不能二次生效。失败响应是否可重试由错误码决定；暂时 503 不永久缓存。

## 5. 队列、outbox 与事件顺序

jobs 领取用 `FOR UPDATE SKIP LOCKED`，短事务递增 fencing_token，lease 默认 60s／20s 心跳；执行结束更新须带 token，旧 worker 不可覆盖接管后的结果。重试指数退避＋抖动，最多次数按任务种类配置；不可重试业务错误直接失败。

后台处理是至少一次，不宣传恰好一次。唯一业务键、版本和有效结果约束确保正式效果不重复。outbox 递交只负责唤醒，消费者从持久 project_events 按 seq 读取；不能以递送成功决定业务是否成功。

project seq 必须在上述项目锁下分配并同事务提交，禁止直接把非提交顺序的全局 bigserial 当可靠 SSE 游标。初始 read snapshot 在 repeatable-read 中取得资源和 eventCursor；后续从该 cursor 重放，消除查询／订阅窗口漏事件。

## 6. 迁移与错误恢复

迁移专用 Job＋PG advisory lock，Server 不在每次启动无锁跑 DDL。新安装、连续升级、失败迁移重试各有测试；release manifest 声明可读 schema 范围。DDL 修改与业务回滚分开，不承诺 Helm rollback 能撤销数据迁移。

上传、模型和沙箱采用状态记录＋补偿任务：对象已上传 DB 未提交→孤儿清理；publish DB 已提交挂载未可见→preparing；外部工具执行未知→核对或人工处理。所有“未知”不得统一重试成重复副作用。

数据库查询、指令和文件均有大小/数量限制；测试时用小上限验证拒绝路径。明确时钟接口供 timeout 测试；业务时间取服务端，不能信客户端时间推进截止。

参考：[PostgreSQL SELECT／锁与 SKIP LOCKED](https://www.postgresql.org/docs/current/sql-select.html)。本文的模块与事务选择是 Judex 工程设计；该资料仅用于核对队列领取所需的锁能力。
