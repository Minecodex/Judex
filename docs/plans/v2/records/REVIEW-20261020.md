## R1：非空项目授权范围没有过滤 CLI 项目列表

优先级：高。状态：**已在隔离 PostgreSQL 复现，未修复**。

`Service.Projects` 只按账号的有效项目成员资格查询，没有使用 CLI principal 的 `ProjectScope`。[实现位置](../../../../internal/collab/projects.go#L15)；HTTP 的 GET 授权只检查 `projects:read`，未在列表结果层补充过滤。

复现：同一账号加入 A、B 两个项目，CLI grant 的非空 projectScope 只有 A。读取 B 详情会被拒绝，但项目列表仍返回 B 的 ID、名称及描述。这不满足原计划对查询与 CLI 的统一授权约束。空 scope 的发现规则需保持明确，不能让非空 scope 的收窄失去效果。

完成条件：非空授权只返回获准项目；补 HTTP／真实 CLI 的两项目回归，并继续验证详情、搜索和事件与授权一致。

## R2：等待人类回应的分支缺少 Web／CLI 回复入口

优先级：高。状态：**后端行为已在隔离 PostgreSQL 复现，客户端缺口已确认，未修复**。

AI 通过 `requiresResponse=true` 请求某人回应后，服务端只在收到对应用户且带 `replyTo` 的消息时解除等待。[等待解除](../../../../internal/collab/messages.go#L190)。正式网页的草稿和发送仅保存正文与提及，没有选择回复原消息的入口，[发送位置](../../../../web/src/features/workspace/Chat.tsx#L15)；CLI 的 `message send`／`push` 同样没有传入 `replyTo`。

复现：AI 请求 B 确认，B 发言并明确 @AI，新的岗位运行完成后，旧 `human_waits` 仍未解除，讨论仍为 active。对照组直接通过 API 提交同一问题的 `replyTo`，等待解除且讨论 settled。

完成条件：补齐可辨认的回复关系、Web 操作及 CLI 参数；精确解除相关等待分支，普通补充不自动唤醒 AI；覆盖多人等待、部分回答、明确 @ 后继续及最终自然收束。

## R3：实时缓存刷新会让旧群配置草稿使用新版本提交

优先级：高。状态：**代码路径确认，尚待浏览器双人并发复现，未修复**。

群设置的名称、目的、工作流与成员只在组件初次挂载时放入本地 state，而保存时读取持续更新的 `group.version`。[草稿与提交](../../../../web/src/features/workspace/dialogs.tsx#L12)。弹窗 key 只有群 ID；SSE 事件会使查询重新获取最新群对象，[缓存刷新](../../../../web/src/features/workspace/context.tsx#L42)。项目一般设置也存在相同的版本取值模式。

触发条件：A、B 同时打开群设置；B 移除成员或修改配置，A 的缓存先收到更新，A 本地表单仍是旧内容。A 保存时提交新版本号和旧成员列表，可绕过预期的版本冲突，覆盖 B 的修改，甚至重新加入刚移出的群成员。

完成条件：草稿保留打开／载入时的基准版本；远端更新提示变化，旧草稿提交必须冲突；保留编辑内容并提供明确重新载入／重试流程。通过两个成员的实际界面与 SSE 验收，断言成员不会被旧草稿意外恢复。

## R4：部分正式查询界面把失败显示为空内容

优先级：中。状态：**代码路径确认，尚待浏览器故障注入，未修复**。

[FileLibrary](../../../../web/src/features/workspace/Files.tsx#L22) 没有处理 `files.isError`；首次查询失败且无缓存时会落入「文件为空」，缺少失败及重试入口。[公共知识界面](../../../../web/src/features/workspace/knowledge.tsx#L20)也没有分别呈现摘要／原文查询的加载和失败状态。

原计划明确要求补齐加载、空态与失败状态。现有文件阅读器具备错误分支，不能据此认定所有相关界面都已完成。

完成条件：统一查询状态组件，区分尚未加载、真实为空、服务失败与权限失效；补文件库及知识读取失败后的重试验收。
