## 独立核对与闭环控制

主会话另做 40 项独立检查：独立群成员/跨公司权限 8 项、固定版本与分享 12 项、真实闭环控制 8 项、三个业务场景各 4 项。每项目当前用户都已加入，可直接在原账号查看。

- 员工无法列出或读取未加入的三级群，也不能访问其他公司的项目；跨公司的两人人类私聊可用，第三方读取被拒绝。
- 普通消息和 record-only 均零触发。员工真实 push 自动唤醒本人岗位；岗位使用公开工具读文件、发布报告并结构化提及下一岗位，不能用纯文本 @ 冒充实际投递。
- 三公司的同一文件均显式更新为 v2；独立下载 v1/v2 核对不同 SHA256 与最新版摘要，原消息仍指向 v1。把 v1 分享至子群仍固定为 v1，子群没有因此出现 AI 运行。
- 单独的真实闭环演练在 `A→B→A` 后 1/1 暂停；暂停期间追加提及及同键重放仍保留原讨论、计数和额度。当前用户在正式 Web 带意见继续一档，随后 2/2 再暂停并手工终止。终止后无活动运行，跨整个剩余观察窗口没有新的 AI 消息。
- 软件、设计分别两次主动评审触发，运营一次。尚未结束的推送/提及合并至原讨论，没有把两版成果伪称为两段独立结束的讨论。人类明确回复只解除相关等待，不自动唤醒模型。

## 真实中断与发现

设计与运营各触发一次 `technical_budget` 暂停，当时闭环计数都是 0；当前用户分别在正式 Web 人工继续一次，同一 run 从检查点恢复并最终完成。它说明累计模型/Token 预算和因果闭环额度是两种限制，也表明多附件、较长工具结果会使单次评审较快消耗技术预算。

设计另有一次 `model_failed`。恢复后运行完成，但提供商级根因没有独立确认，不能据此宣称服务稳定性已经证明。有一笔历史模型请求仍保留 started/未知结果账本，预留成本未清零；本轮 101 次模型请求中，100 次有完成结果，1 次结果未知。已知 usage 为输入 2,432,654、输出 33,162 token，未知请求不按 0 Token 计算，也不估算账单。

软件 QA 初次把自己附加检验脚本中的 SQLite 跨线程连接错误归因到交付测试。员工用原始文件和多次重测提出反证，QA 后续明确撤回错误归因，确认下载 v2 的 18 项测试通过；最终产品建议由员工确认。这是一项被证据纠正的模型误判，不能隐藏，也不能转写为未经证实的产品缺陷。

CLI 已支持显式文件更新并自动发布对应文件消息；`message send` 尚无直接引用任意已上传版本的 `--file-version` 参数。软件/设计按声明的回流方式补发新包，会产生独立文件，保留为可改进的交互点。员工曾尝试不支持的 `auth status`；当前文档写的是 `judex status`，此项仅记为测试命令尝试错误，不记作产品/文档合同错误。

员工设计会话曾生成独立浏览器验证报告；主会话未把其结果计入本轮 CUA 浏览器证据，而是用现有 Chrome 对正式项目、HTML v2 预览、预算继续和闭环控制独立检查。

三个 Codex 会话均已完成并保留：软件 `01a1596f-bfb9-7030-9b8c-b4f1b0b841f3`，设计 `01a1596f-c60b-78e2-8cd2-b59ca0c7d49d`，运营 `01a1596f-cc6b-7b51-930e-034b73e30d00`。每个会话使用独立合成员工设备 grant，scope 限一个项目；凭据不进入提示词/仓库/报告。
