## R10：没有聊天活动时，项目配置冲突后无法从表单恢复

优先级：中。状态：**两位管理员真实浏览器表单＋隔离 HTTP／PostgreSQL 已复现，未修复**。

[projects.go:68](../../../../internal/collab/projects.go#L68)更新项目后没有发布项目配置变更事件。[context.tsx:33](../../../../web/src/features/workspace/context.tsx#L33)只在写成功时刷新查询，收到 VERSION_CONFLICT 时仅显示提示；[ConfigChange](../../../../web/src/features/workspace/ui.tsx#L54)的重新载入入口又依赖查询已经获得更高版本。默认关闭窗口聚焦刷新，staleTime 本身不会触发定时读取。

复现：两位管理员打开同一项目设置。甲保留本地草稿，乙通过真实表单保存新描述，项目变为 version 2；乙没有额外发聊天消息。甲既没有远端更新提示，也没有重新载入入口。甲连续两次保存均以 expectedVersion=1 返回 HTTP 409，草稿保留但无法通过当前表单取得最新配置。按提示关闭、重新打开项目设置，仍显示 version 1 的旧描述，而数据库已经是 version 2。

影响：服务器正确阻止了覆盖他人的修改，但前端的冲突恢复流程没有闭合，用户需要整页刷新或依赖无关活动触发查询；关闭重开表单的现有提示不足以恢复。未发生数据库覆盖或配置数据丢失。

此前 [browser-followup.mjs:16](../../../../tests/v2/browser-followup.mjs#L16)在乙保存项目后额外发送 `Project update refreshes the shared queries.`，这条消息带来的 SSE 刷新掩盖了配置自身不通知的问题。R3 固定编辑基准版本的修复仍有效，但不能据此证明配置变更与冲突刷新链路完整。

完成条件：配置变更发布授权范围内的刷新事件；409 后主动获取最新配置并保留本地草稿，提供明确重新载入入口。补两位用户仅修改配置、没有额外聊天消息的回归，同时审计职位、工作流、成员和个人提示词的同类接入。

证据：`.cache/v2-review-3/project-conflict.json`、`project-conflict.png`；记录包含乙的 HTTP 200、甲的两次 409 和各自提交的版本。另通过浏览器实际观察关闭重开仍为 `Original project description`。

## R11：写入成功但响应正文损坏后，重试会重复执行

优先级：中。状态：**正式前端＋真实 HTTP／PostgreSQL＋故障代理已复现，未修复**。

[client.ts:62](../../../../web/src/lib/api/client.ts#L62)在响应正文读取、解析和验证前，只要 HTTP 状态小于 500 就移除 pendingWrites 中的幂等键。[client.ts:65](../../../../web/src/lib/api/client.ts#L65)将 JSON 读取错误变为 null，随后访问 payload.data 触发 TypeError。聊天输入保留原草稿，但下一次提交已失去原幂等键。

复现：测试代理先让消息真实提交，保存上游 HTTP 200 的完整成功响应，再仅将返回浏览器的 JSON 正文破坏。数据库已有第 1 条消息，界面报 `Cannot read properties of null (reading 'data')`，原草稿保留。再次点击发送相同草稿，前端生成不同 UUID 幂等键；第二次 HTTP 200，数据库出现同作者、同内容、不同 ID／seq 的第 2 条消息。

影响：用户把失败草稿重试一次，可能重复发言。公共 request helper 用于其他业务写入，因此需要统一处理不确定响应；本轮只实际复现普通消息，没有执行岗位或调用真实模型，不把重复 AI 运行描述为已观察事实。普通 fetch 网络错误已有保留幂等键的分支，本发现针对“已收到成功状态，但正文无法正确读取／解析”的路径。

完成条件：只在响应可确认为成功或明确拒绝后结束该写入意图；正文中断、非法 JSON／无效 envelope 等不确定结果保留原键，并返回可理解的恢复状态。补真实提交后损坏响应、同草稿重试仍只有一次副作用，以及新意图正常获得新键的回归。

证据：`.cache/v2-review-3/ambiguous-write.json`、`ambiguous-write.png`。两个 POST 的业务 JSON 完全一致、幂等键不同、服务器均返回 200；第一个成功响应对应第 1 条数据库消息，第二次对应第 2 条。
