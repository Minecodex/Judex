## 2. 分栏建议

左侧全局导航保持固定，群列表、聊天、阅读区组成三个可调整内容区域。

1. 两条分隔线支持拖拽；视觉细线与较宽的命中区域分开，悬停提示拖拽。支持键盘调整宽度。
2. 默认比例可从约 20%／45%／35% 起步，具体按可用桌面宽度验证。
3. 折叠判定结合最小可用宽度和继续向边缘拖动的距离，避免仅按百分比导致不同屏幕上误折叠；到达阈值先反馈折叠预览。
4. 三个内容区域都能显隐，但至少保留一个。按用户后续反馈改为固定导航栏一个「布局」图标菜单，各区域标题放轻量收起图标；恢复入口不能放在已经隐藏的区域内部。
5. 恢复时回到上次有效宽度；提供恢复默认布局。阅读聚焦模式退出后恢复原分栏。
6. 折叠不清除消息草稿、滚动位置、选中文件或固定版本；点击消息文件卡片自动展开阅读区。
7. 按用户保存宽度及显隐偏好；界面偏好不影响权限、消息和讨论执行状态。
8. 文件库与文件阅读共用右侧区域的分栏能力，避免打开文件库时出现另一套尺寸和行为。

这属于界面布局能力，可沿用 HeroUI、统一 token 和现有 Zustand 偏好管理；不需要改变群与讨论领域。

## 3. 文件阅读范围建议

不存在有意义的固定“最大格式数”：很多代码扩展名共用同一个阅读器，能展示原文也不等于具有适合该格式的阅读体验。建议以约 40～60 个常见扩展名作为首期候选范围，按实际样本验收逐项确认；下面是能力候选，不是当前已支持清单或全部必须一次交付的承诺。

| 阅读类别 | 候选扩展名示例 | 建议阅读体验与边界 |
| --- | --- | --- |
| Markdown／文本 | md、markdown、txt、log | 排版、目录、搜索；日志和原文可选换行 |
| 代码 | go、py、js、ts、tsx、jsx、java、rs、sql、sh、css 等 | 高亮、行号、搜索、复制；语言支持复用同一阅读器 |
| 结构化数据／配置 | json、jsonl、yaml、yml、xml、toml、ini | 原文和结构视图；大文件分页或按块读取 |
| 分隔表格 | csv、tsv | 表头、横向滚动、列宽、排序／筛选、大表虚拟渲染、编码与分隔符识别 |
| 电子表格 | xlsx、xls、ods | 工作表切换、单元格、数值格式及合并单元格；公式缓存值与重新计算分别界定，保留 PDF 版式预览 |
| PDF／文字文档 | pdf、docx、doc、odt、rtf | 分页、缩放、搜索；Office 先转换预览，复杂版式以实测为准 |
| 演示文稿 | pptx、ppt、odp | 幻灯片缩略图和逐页查看；不承诺动画和交互对象完整还原 |
| 图片 | png、jpg、jpeg、gif、webp、svg、bmp、avif | 缩放、平移、适应窗口；新增类型要扩展验证或转换，不只增加前端扩展名判断 |
| HTML／网页资源包 | html、htm、含 index.html 的 zip | 隔离预览、资源相对路径、切换源码与页面；延续身份核验和预览会话 |
| 音频 | mp3、wav、ogg、m4a、flac | 播放、进度、音量；实际可播取决于编码 |
| 视频 | mp4、webm；mov、mkv 按需转换 | 播放、进度、全屏；容器与编码分别检测，不保证凭后缀直接播放 |
| 图示／归档 | mmd、mermaid；zip、tar、gz、7z 等 | 图示专用渲染；归档目录及获准条目预览。图示与归档仍由不同适配器处理 |

PSD／AI／Sketch／FIG／CAD／三维模型建议后置：先采用导出的图片、SVG 或 PDF；原生解析的可行性、还原程度及运行成本另行评估。TIFF／HEIC、EPUB、Draw.io／Excalidraw 等也可在真实需求出现后增加。

建议顺序：先 CSV/TSV 真表格、代码/结构化数据、统一图片/PDF 工具栏，再补 Excel 工作表阅读、文档/幻灯片转换扩展，随后加入媒体和专用格式。

实现应由格式识别、阅读器注册、转换回退与统一工具栏组成，不能每个后缀建设独立页面。文件大小、页数/行数与超限行为需要按阅读器明确；失败时提供原因、重试或下载。

所有阅读方式延续固定版本与会话授权：分享版本不会因为新版存在而切换，格式转换不会开放来源群其他文件，查看能力不自动意味着在线修改能力；以后编辑也应产生明确的新版本。

技术依据：

- [Papa Parse 官方文档](https://www.papaparse.com/docs)支持 CSV 分隔符、表头、流式解析与 worker；可作为解析层，表格 UI 另行实现。
- [SheetJS 格式清单](https://docs.sheetjs.com/docs/miscellany/formats/)覆盖多种电子表格；读取数据不等于完整 Excel 版式与公式引擎。
- [MDN 媒体容器说明](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Containers)说明容器和编码的关系；音视频支持需按实际编码确认。

## 4. 当前卡片的语义、样式和触发

| 当前能力 | 触发 | 现有呈现／动作 | 语义 |
| --- | --- | --- | --- |
| 人类回应请求 | 岗位 AI 结构化提及某人且 requiresResponse=true | 普通聊天消息下的回应提示，用户引用原消息回复；等待时有“等待人类回应”提示 | 等待该人的回答；没有同意／拒绝按钮 |
| 讨论暂停卡片 | 闭环达限，或技术预算、模型／上下文／工具等异常导致暂停 | 主题适配卡片、边框圆角、次数标签、原因和可选意见；橄榄色“继续讨论”、中性“终止本次讨论” | 继续给予讨论执行额度；终止整段讨论，不代表业务方案被批准／否决 |
| 工具结果核对 | 工具副作用未知，需要岗位关联人核对 | 公共知识的运行页内，岗位本人可见工具日志和核对表单；确认已执行／授权重试一次 | 核对执行事实，保存后仍需单独继续；并非每个工具执行前都弹审批 |
| CLI 设备授权 | CLI 登录产生设备码，网页打开授权页面 | 独立授权卡片，设备／账号／权限范围；主按钮确认授权、危险色拒绝 | 允许或拒绝该设备访问，与群内方案意见无关 |

项目／群成员直接加入，无邀请同意／拒绝卡片；旧版计划、任务、交付与业务审批链已移除，参考工作流不自动产生审批节点。

## 5. 可讨论新增：请求意见卡片

如需在群内明确记录方案选择，建议增加轻量的“请求确认／征求意见”卡片，复用人类回应分支，不恢复强制业务状态机。

例：品牌设计岗位请求李明确认“是否采用方案 B？”，附方案说明和品牌规范 v2 的固定引用。卡片提供“同意此建议／需要修改／补充意见”，并显示提问人、指定回应人及回应状态。

- 使用统一浅色／深色表面、细边框和橄榄色主操作；不同意是正常业务反馈，不应一律用危险红色。
- 响应保存真实作者、选项、意见、时间与原消息引用。只由指定人员回答自己的请求，多人请求分别记录，重复提交不重复执行。
- 不同意可附修改建议，并解除该人的待回应分支；不自动终止整段 AI 讨论，也不改变项目完成状态。
- 只有明确提交的结构化请求才生成可点击卡片，不能把 AI 正文里出现“同意／拒绝”解析成有执行效力的按钮。
- 普通提交只记录回应。如需岗位继续，提供清晰的“提交并 @该岗位继续”操作，保持只有明确提及才触发 AI 的既定规则。
- 讨论已暂停时，该回应进入上下文，不绕过暂停和额度；仍由现有继续／终止卡片控制恢复。
- 付款、发布、采购、删除等产生外部业务效果的授权不因点击“同意此建议”自动获得，若未来接入需另行定义作用对象与执行合同。

## 6. 后续实现前需要收口的选择

1. 首期格式清单及各格式的还原程度，尤其 Excel 是数据阅读还是高保真 Office 查看。
2. 三栏折叠阈值、恢复按钮位置及阅读聚焦行为，通过桌面原型验证后固定。
3. 是否新增请求意见卡片；若新增，明确指定回应人、是否允许多选、请求失效和再次提问的交互。

以上均为本轮讨论建议；现有 V2 合同及已验收行为保持原含义。
