# 01 产品边界与身份权限

## 1. 已确认的使用形态

Judex 是公司内部部署的协作平台，员工可以自由注册账号并创建项目。平台业务层不设置员工等级、公司主管链或“第一个注册的人自动获得全平台业务权限”的机制。

2026-09-27 用户澄清：“任意用户”指内网任意用户，不是要求开放公网注册；自由注册不授予其他项目的访问与审批权限。

同一个人可以在项目 A 中是创建者，在项目 B 中是普通成员，在项目 C 中承担特定验收职责。角色按项目和具体工作分别计算，不跨项目继承。

内部部署不等于所有登录账号可访问全部项目。自由注册 / 创建项目与加入别人项目是两件事：已有的管理者邀请、指定职位规则继续有效；未确认开放自助加入。

2026-09-27 已确认首版内网开放注册、邮箱作为登录名＋密码，不依赖邮件验证；不能显示“已验证企业身份”。SSO 保留适配边界，不新增注册审批。非成员项目目录、账号停用与恢复的工程方案见 [V1 身份计划](../plans/v1/02-身份项目与配置.md)，部署级恢复不授予全局业务审批权。

## 2. 六种不同对象

| 对象 | 含义 | 生命周期 |
| --- | --- | --- |
| User | 注册员工账号 | 跨项目使用 |
| ProjectMembership | 某账号在某项目中的成员关系与管理角色 | 项目内有效 |
| PositionTemplate | 用户定义的职位名称、职责提示词、流程节点挂载 | 属于项目 |
| AgentIdentity | 一份持续存在的机器人 / 任职身份 | 与业务历史一起保存 |
| IdentityBinding | 任职身份当前绑定的人及绑定版本 | 可替换，有历史 |
| AgentRun | 某身份在某议题的一次执行 | 可结束、失败、取消或恢复 |

一人可承担多个任职身份；同一个职位模板可产生多份分别关联不同人员的身份。任务不是按同岗人数复制。

项目中的主要展示是“人 + 职位”，但数据库和运行记录仍关联稳定身份。历史决定另记实际操作者，不能随绑定改变而修改署名。

## 3. 注册与项目创建

设计路径：

1. 员工提交注册信息；依据最终选择的账号验证机制确认账号归属。
2. 完成登录后获得创建项目能力，没有全局项目审批权。
3. 创建项目时，在同一事务中写入项目、创建者的项目成员关系和创建事件。
4. 创建者在该项目内拥有创建者 / 管理能力，配置项目流程、职位、成员与授权。
5. 创建者若承担具体工作，也须有明确任职身份和工作职责；创建项目不隐式把所有机器人绑定给本人。

“公司内部人员”的识别可通过内部网络、企业邮箱验证或企业身份源实现，首版采用已确认的内网部署与邮箱密码登录，不声称完成企业邮箱归属验证。内部网络边界不替代账号认证。

## 4. 项目邀请与已有成员任职

- 管理者发送项目邀请时选择一个或多个职位；接受邀请后按这些选择建立任职身份。
- 受邀者不能在接受过程中抢占已有身份或自行扩大职责；之后可配置自己的项目提示词。
- 对已有成员，管理者可以明确分配新的任职身份；这是新增岗位承担关系，不是替换另一人的身份。
- 替换关联人时保留 identity_id，只更新当前绑定并递增 binding_version。原人的个人偏好、凭据不转移。
- 所有关系写入均须检查人员属于该项目、职位属于该项目、被替换版本仍有效。

设计建议：绑定变更后重新验证待决事项的当前可操作人；撤销旧会话能力凭据或在工具入口检查新绑定版本，不能等旧 Token 自然到期才落实。

## 5. 授权矩阵

下表区分管理权、岗位职责和业务决策权。

| 动作 | 允许主体 | 不应推导出的权限 |
| --- | --- | --- |
| 注册、创建项目 | 符合注册机制的员工 / 已登录员工 | 访问其他项目 |
| 配置项目职位、流程、邀请成员 | 本项目创建者或获授权管理者 | 任意任务验收、读取他人私人提示词 |
| 普通讨论、资料提交 | 有访问范围的项目成员或被授权工具 | 正式采纳材料、批准工作变更 |
| 上报本人职责工作 | 当前绑定人或被其授权的本地工具 | 代表其他身份上报 |
| 确认发送交付 | 相应来源的当前有权人 | 替其他来源一次性确认发送 |
| 接收 / 拒收交付 | 接收职责的当前有权人 | 代替任务最终验收 |
| 任务最终验收 / 重开 | 当前有权验收人 | 凭项目管理身份自动验收 |
| 计划整体验收与状态更新 | 计划负责人 | 其他项目创建者兜底修改 |
| 同一提议的明确代批 | 符合项目流程授权的主管或项目创建负责人 | 自动代批全部事项、伪记为原人亲自操作 |
| 执行 AI 工具 | 当前运行的受限能力 | 人工审批能力、直接写业务数据库 |

“主管”指项目中的明确统筹授权，不因员工在现实公司的职级自动获得权限。最新平级账号制度不取消项目内既有的代批规则。

## 6. 可见性与提示词

Q074 已确认：项目共享业务资料对本项目成员与本项目获授权运行的 Agent 统一可读，不设置逐文件、逐岗位读取白名单。读取入口校验项目成员 / 执行身份和项目归属；其他项目不能借文件 ID、挂载或签名地址读取。可公开的项目名称目录仍需 D02 决定。

私人提示词、密钥、私有执行上下文和未提交工作目录不进入项目共享区。它们继续按本人 / 运行身份处理，与共享业务文件是不同存储类别。资料可读不授予业务审批、原件写入或部署运维权限。

岗位职责、岗位经验和获准的业务会话随稳定身份保留。个人工作提示词按项目、本人、职位独立配置，只用于本人在对应职位的当前有效绑定身份，不因此向主 Agent、管理员或接任者公开原文。一个人的多个职位不共用一条项目通用提示词。

`list_agent` 返回可发现身份、公开职责和可调用范围。个人偏好由上下文构建器在授权执行中注入，不将全部个人配置作为主 Agent 的目录信息返回。

## 7. 技术运维与业务权限

K8s 管理、备份恢复、模型密钥配置属于部署运维能力，不映射为产品内“所有项目都可审批”的账号。数据库运维在技术上能接触数据，不应被宣传为对运维人员不可见；是否需要额外加密、密钥托管和审计要求待实施评审。

当前不擅自新增全局业务超级管理员。账号恢复、离职停用、最后负责人恢复的 V1 工程方案见 [身份计划](../plans/v1/02-身份项目与配置.md)：受审计部署运维操作，不授予全局业务审批权。
