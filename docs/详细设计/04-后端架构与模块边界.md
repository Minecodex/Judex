# 04 后端架构与模块边界

## 1. 架构基线

已确认：Go + Gin，前期模块化业务单体。自研业务 API、授权、状态机和后台调度在一个代码库、一个主要业务服务中实现；不按项目、计划、审批分别部署微服务。

设计方案：一个 `judex-server` 负责业务控制，Agent harness（模型调用、上下文组装、工具循环）作为 `internal/agent` 模块在 judex-server 进程内运行。经核验 OpenSandbox 为外部驱动架构：客户端在沙箱外经 SDK/API 创建沙箱、远程执行命令与文件操作，并遵循“密钥不进沙箱”原则；因此沙箱是纯执行环境，不运行自研常驻程序，不维护第二套业务数据库。OpenSandbox 作为第三方基础设施使用，其实现语言不改变自研业务选择。

前端构建产物可以随 Server 镜像发布，由 Gin / 静态服务模块提供。前端路由回退、缓存策略与 API 前缀分开，不能让 API 404 返回 SPA 页面。

## 2. 代码布局方案

```text
cmd/
  judex-server/       HTTP、后台 worker、Agent harness 与启动装配
  judex/              本地 CLI（协议与授权确定后实施）
internal/
  identity/          账号、会话、凭据
  project/           项目、成员、职位、任职与邀请
  work/              计划、任务、分工、前置条件
  decision/          提案、审批位、代批与审阅版本
  handoff/           来源交付、发送、接收、补交
  discussion/        议题、消息、关联对象
  material/          文件版本、上传与访问范围
  workflow/          流程规则、节点、发布版本
  agent/             运行调度、服务端 harness、上下文、工具策略与沙箱派发
  job/               持久后台任务与提醒
  audit/             正式事件与访问追溯
  transport/http/    Gin 路由与协议 DTO
  infrastructure/   PostgreSQL、S3、OpenSandbox、模型适配
```

单文件遵守现有 2000 行上限。模块通过明确的应用服务 / 接口合作，不越过模块边界直接修改别人的数据表。

## 3. 依赖方向

```text
Gin handler → application command/query → domain policy → repository interface
                                                ↑
                          PostgreSQL / S3 / Sandbox adapter
```

HTTP 层负责认证上下文、解析、基础校验、错误映射和响应，不承载长流程状态机。业务模块不依赖 Gin 类型；后台任务不得持有 `*gin.Context`。

建议使用 PostgreSQL 驱动 pgx 与 sqlc 管理显式 SQL，迁移工具待定。它们是工程建议，不是 Q057 已经同时批准的依赖。接口契约采用 OpenAPI 草案，由实现校验生成客户端。

## 4. 正式命令事务

以“接受一份交付”为例：

1. 验证登录人 / 授权工具身份，读取项目成员与当前任职绑定。
2. 按目标 ID 与预期版本锁定交接来源，确认其仍为待接收。
3. 核对接收职责、来源版本、依据版本、受影响状态。
4. 条件更新来源，记录实际操作者、来源渠道和决定版本。
5. 同事务写入业务事件与后续处理任务。
6. 事务提交后向客户端返回已记录的决定；后续 AI 分析异步运行。

后续任务的执行不能反向冒充这次人的决定。模型失败也不能回滚已经成立的人类审批；应把后续分析标为失败 / 待重试。

## 5. 后台任务

设计方案：前期使用 PostgreSQL 持久任务表或基于 PostgreSQL 的队列库；River 是候选，未锁定。避免仅以进程 goroutine、内存 channel 或定时器保存待执行业务。

任务类型包括：材料解析、Agent 调度、状态提醒、共同审批超时扫描、索引、对象清理和事件投递。业务提交与入队须可在同一事务完成，或以事务 outbox 实现可靠衔接。

- 每个任务有任务 ID、幂等键、可运行时间、重试次数、租约 / 执行状态。
- worker 异常后允许重新领取；处理器以幂等状态转换防止重复副作用。
- 同一议题会话续接串行化，独立子 Agent 可以并行。
- 接收提醒和审批到期分别建任务，不复用一个“超时自动成功”处理器。
- 外部工具结果不确定时进入核对流程，不盲目重跑可能已完成的操作。

## 6. HTTP 与实时事件

使用 REST 命令 / 查询接口。设计建议首版 SSE 传递消息增量、执行进度及业务事件；以事件 ID 恢复断线，服务端数据库记录为准，不将 SSE 当作可靠队列。

用户关闭网页或 HTTP 请求取消不应直接取消已登记的持久运行。运行取消使用独立、有权限校验的命令；后台使用自身生命周期 Context。

建议中间件包括请求 ID、认证、项目范围提取、错误映射、结构化日志、恢复 panic、请求体限制及速率限制。panic 恢复只保护 HTTP 进程，不提供事务成功或后台执行保证。

## 7. 服务数量与扩展边界

首期自研业务服务一个。沙箱按运行按需创建、结束回收；Agent harness 不再是独立部署的自研执行程序，随 judex-server 进程运行，负载增大时可按 worker 模式单独部署同一镜像。

PostgreSQL、SeaweedFS、OpenSandbox 生命周期服务和 Controller 是部署组件，不按“业务单体”要求塞进同一个容器。实际 Pod 数取决于数据服务拓扑与沙箱并发，不能把一个 Helm Release 等同于一个 Pod。

当后台负载实际影响 API 响应时，可以使用同一代码 / 镜像的 worker 模式单独部署，保持业务模块和协议不变；这不是当前必须先拆服务的要求。

## 8. 观测与配置

日志关联 request_id、project_id、identity_id、run_id、job_id、trace_id。业务审计与调试日志分别存储，私人提示词、模型凭据和完整附件默认不进入普通日志。

运行配置按连接、模型、队列、沙箱、文件限制和认证分组。密钥通过 Secret 注入或引用；配置变更与模型参数快照须能追溯。具体观测后端、限额数值和模型供应商接口尚未选定。

### 8.1 OpenSandbox 实测契约（v0.2.2，2026-09 实测锁定）

`internal/infrastructure/opensandbox` 按以下实测协议适配（部署环境变量 `JUDEX_OPENSANDBOX_ENDPOINT` / `JUDEX_OPENSANDBOX_API_KEY`，未配置时沙箱工具返回 SANDBOX_UNAVAILABLE，不静默成功）：

- 认证：自定义头 `OPEN-SANDBOX-API-KEY`（非 Bearer）。
- 创建沙箱：`POST /sandboxes`，体为 `{"image":{"uri":...},"entrypoint":[...],"resourceLimits":{"cpu":"500m","memory":"256Mi"},"timeout":秒}`；Controller 会向每个沙箱注入 `bootstrap.sh` 与 `execd` 守护进程，`entrypoint` 只承载保活命令（`sleep infinity`），不得用来启动 execd。
- execd 固定监听 **44772** 端口，经代理访问：`POST /sandboxes/{id}/proxy/44772/command`，体 `{"command":"..."}`，返回 NDJSON 事件流：`init` / `stdout` / `stderr` / `execution_complete`（成功）/ `error`（失败，`error.evalue` 为退出码）/ `ping`（保活）。流中断（无终止事件）按 unknown 处理，不盲重试。
- 状态：`GET /sandboxes/{id}` → `status.state` ∈ Pending/Running/Failed；回收：`DELETE /sandboxes/{id}`。
- execd 无独立文件 API：read/write 经 base64 管道保证字节精确。
- 每次 `/command` 为独立 shell，工作目录不跨命令保持。
- Agent 侧为“一次运行一个沙箱”：`RunSandbox` 惰性创建（首次沙箱工具调用触发）、运行内复用、结束即回收；未配置时工具诚实报错。
