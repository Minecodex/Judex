# 跨议题记忆选型讨论

日期：2026-09-24。状态：V2-Q013、Q014 的记忆使用边界已确认；开源方案仍为调研候选，未安装、部署或开展 Judex 场景实测，尚未选择依赖。

## 1. 已确认的设计依据

- 主 Agent 保持一个身份，按议题保存不同会话，关联议题通过引用衔接。
- 子 Agent 同一议题续接，跨议题按需加载业务知识，单次探索上下文分别管理。
- 主 Agent 不自动获得子 Agent 的全部权限，转交内容仍需检查接收范围。
- AI 形成草稿；正式采纳、交付接受、工作安排变化仍由有权的人决定。
- 材料可先登记原文、来源与时间，人在确认时可以补充用途。
- 机器人是稳定主体，绑定的人可更换；一人可以绑定多个机器人。
- V2-Q013：AI 提炼的经验可以在有权限的其他议题中作为线索使用，但标明“AI 归纳、待验证”并附依据，不能直接成为正式规则或承诺。
- V2-Q014：默认限定当前项目及已授权共享知识；通用经验经确认和明确授权后才可跨项目复用，保留来源与适用条件。

用户已知 Mem0，希望比较其他开源选择。本轮不增加后台触发成员本地 AI 的能力。

## 2. 推荐结论

建议优先验证 **Hindsight**，以 **Mem0 OSS** 做对照。两者都可通过记忆服务或 SDK 接到自有 harness，不需要先改变主、子 Agent 调度模型。

- Hindsight 优先验证岗位经验提炼、来源关联和跨议题回顾。
- Mem0 作为较直接的提取与检索接口对照，检查较少的记忆处理机制是否已经满足需要。
- 如果核心体验是跨事件关系、历史变化与关联查询，增加 Graphiti 验证。
- 如果还要统一资源、记忆和 Skills 的目录式检索，单独评估 OpenViking；这比只补充记忆层涉及更大的上下文组织范围。
- Letta 适合参考长期 Agent 身份与记忆管理，但其完整 harness 与当前自建运行机制存在职责重合，暂不作为首选独立记忆后端。

以上是基于能力匹配的工程判断，不是性能排行。候选应分别验证，不建议首轮叠加多个后端。

## 3. 项目比较

| 项目 | 核心定位 | 对 Judex 的适配判断 | 当前核心许可证 |
| --- | --- | --- | --- |
| [Mem0](https://github.com/mem0ai/mem0) | 可嵌入或自部署的记忆提取与检索 | 适合作为基础对照；正式状态、权限与来源关联仍由 Judex 管理 | Apache-2.0 |
| [Hindsight](https://github.com/vectorize-io/hindsight) | 长期事实、经历、证据归纳与回顾 | 更贴近岗位经验积累，可优先验证 | MIT |
| [Graphiti](https://github.com/getzep/graphiti) | 带来源与时间变化的实体关系图 | 适合复杂关系和历史查询，需要图存储及相关运维 | Apache-2.0 |
| [OpenViking](https://github.com/volcengine/OpenViking) | 统一资源、记忆、技能的目录式上下文数据库 | 与文件式探索契合，但范围大于单独记忆服务 | 主项目 AGPLv3；CLI、部分示例另有许可 |
| [Letta Code](https://github.com/letta-ai/letta-code) | 有状态 Agent harness，包含身份与记忆管理 | 参考设计，避免为了记忆被动替换现有候选运行架构 | Apache-2.0 |

许可证按本轮官方仓库标注记录，实际采用时需要核对固定版本、组件和发行方式；不将托管产品功能等同于 OSS。

### Mem0

新版 OSS 提取改为 ADD-only，显式更新、删除与历史 API 仍可用；旧的自动 ADD/UPDATE/DELETE 提取流程不能沿用，OSS Graph Memory 已移除。[迁移说明](https://docs.mem0.ai/migration/oss-v2-to-v3)

有用户、Agent、运行范围与 metadata 过滤，可使用库或自部署服务；组件包括模型、embedding 和向量存储。[OSS 概览](https://docs.mem0.ai/open-source/overview)

对 Judex 的推论：保留新旧记忆有利于追溯，但当前哪条结论有效仍需业务依据；身份过滤不能替代机器人和项目的授权。服务端映射稳定 robot_id，不应将岗位经验全部绑定在可更换的真人 ID 上。

### Hindsight

提供 retain、recall、reflect 操作，支持按 Bank 组织记忆、生成证据归纳和持久综合内容，并提供 HTTP 与多语言客户端。通常采用 PostgreSQL 与相应索引组件。[官方仓库](https://github.com/vectorize-io/hindsight)

需要验证来源追溯、文档替换以及检索筛选行为；自动归纳和综合回答仍属于 AI 产物。[官方最佳实践](https://github.com/vectorize-io/hindsight/blob/main/skills/hindsight-docs/references/best-practices.md)

自部署可通过鉴权、租户与操作校验扩展集成授权，不能把一个 Bank 名称或标签过滤当成完整业务权限。[扩展说明](https://hindsight.vectorize.io/developer/extensions)

对 Judex 的推论：可以让其整理可复用经历，但自动形成的观察与观点必须带来源和候选状态；不能自动改写人的决定。Bank 的划分需要匹配权限边界，避免综合不同可见范围的材料后生成可被错误共享的记忆。

### Graphiti

以来源 episode 为依据提取实体和关系，记录有效时间及被后续信息替代的关系，支持关系与历史检索。Graphiti 是开源框架，不能等同于带治理和托管能力的 Zep 产品。[官方仓库与产品对比](https://github.com/getzep/graphiti)

对 Judex 的推论：适合回答“这个约束来自哪些事件”“某个时期使用什么安排”，但正式任职、批准与变更应直接取自业务记录。模型推断出的关系不能成为实际授权依据。

### OpenViking

使用 `viking://` 虚拟目录组织资源、记忆和技能，支持按目录摘要逐层读取及会话提交后的记忆提取。[官方介绍](https://github.com/volcengine/OpenViking/blob/main/docs/en/getting-started/01-introduction.md)

当前已有账号、用户和可选资源 ACL；具体的机器人、个人和项目身份仍需 Judex 映射。[认证说明](https://docs.openviking.ai/en/guides/04-authentication)

主项目当前为 AGPLv3，不应根据早期文章记为 Apache-2.0；开源服务器与商业版范围也不同。[官方仓库](https://github.com/volcengine/OpenViking)

对 Judex 的推论：适合进一步研究四工具如何探索资料与记忆。不过目录组织本身不能证明其能处理任职替换、权限撤销或人工正式化，仍需场景验证。

### Letta

当前官方入口将活跃源码指向 Letta Code，原 V1 服务源码为历史版本。[官方入口](https://github.com/letta-ai/letta)

当前记忆设计包含 Agent 所有的记忆文件、按需读取和后台整理等机制。[当前记忆文档](https://docs.letta.com/agent-sdk/memory)

对 Judex 的推论：其“身份长期存在、会话持续积累”的思路可借鉴，但直接引入完整运行机制会扩大选型范围。先保持自有 harness 与记忆后端可独立替换。

## 4. Judex 应保留的记忆边界

建议区分以下信息：

| 信息 | 示例 | 处理方式 |
| --- | --- | --- |
| 当前正式事实 | 当前负责人、获批方案、正式日期 | 以业务记录为准，查询时按权限获得当前版本 |
| 原始材料与议题历史 | 上传报告、人的答复、机器人返回 | 保留来源、时间和版本，作为可追溯依据 |
| 可复用经验 | 过去为什么采用某方法、某方案曾失败的原因 | 记忆引擎整理与召回，区分事实引用和 AI 归纳 |
| 本次运行上下文 | 当前问题、已读材料、待回收调用 | 由 harness 续接或压缩，不取代长期业务记录 |

Q029 确认人可以在议题 Chat 提供问题、信息、证据和文件。这些输入可作为记忆的来源，但记录应区分“某人说过什么”、其证据及 AI 后续归纳。Q030 进一步确认 Web 普通聊天保持讨论性质；正式批准应引用实际审批事件，不能因聊天出现“同意”就提炼出一条已经批准的结论。本人明确指示下的 CLI 正式审批按其真实事件和来源记录。

“以前采用过方案 A”与“当前必须采用方案 A”具有不同业务含义。候选记忆可以帮助检索旧决定，但当前结论应核对正式来源。

后续 Q020 已引入主管兜底与多人审批首人通过后的超时默认同意。记忆引用正式决定时，应保留原审批记录中的同意来源；不能把系统规则生效归纳成每个参与者都亲自明确同意。具体审批规则仍以整体讨论中的最新决定为准。

建议将记忆视为可纠正、可重建的辅助检索层。与业务记录关联时保留：组织、项目、机器人、来源议题、原文或产物引用、源版本、发生时间、登记时间、可见范围及确认状态。该信息由 Judex 控制，不依赖模型在自由文本里自行声明身份。

V2-Q013 已确认 AI 归纳出的经验可以未经人工确认，在有权限的其他议题中作为待验证线索使用。必须标明“AI 归纳、待验证”并附依据；召回、转述或多次使用都不使它自动成为正式规则或承诺。

## 5. 接入统一 harness 的候选方式

1. 发起某机器人运行时，根据项目、机器人身份、当前议题和问题，确定获准检索范围。
2. 读取当前正式背景，检索相关历史经验，向模型提供少量摘要、来源引用和确认状态。
3. 需要更多依据时，机器人通过获准的资料入口继续读取。主 Agent 调用子 Agent 不合并双方权限。
4. 议题取得阶段结果后，提取候选经验与索引；人的新决定更新正式来源，记忆侧标记相关变化。
5. 所有框架生成的综合结论都保留“AI 归纳”身份，不能替代审批记录。

记忆服务可以通过 harness 的上下文装配阶段或受控平台 CLI 接入，不要求因此再增加模型工具数量。模型也不能凭自己填写的 project_id、bank_id 或过滤参数扩大检索范围。

权限检查应覆盖检索、按 ID 读、更新、删除及后台归纳。来源权限收紧时，相关派生记忆与缓存也需要停止向无权角色提供；多个来源合成的摘要不能因为换了表达方式就自动扩大可见范围。

Q028 已明确执行过程与业务历史持续归机器人。记忆应关联稳定机器人及项目范围，更换绑定人不迁移、复制或重建岗位记忆，新绑定人直接访问机器人已有业务历史；不引入交接确认。个人设置另行归属。Q014 的跨项目边界继续有效：默认当前项目及已授权共享知识，通用经验经确认和明确授权后才跨项目复用，保留来源与适用条件；同一人绑定多个机器人不自动扩大资料共享范围。

## 6. 先验证的真实问题

建议使用相同的中文材料、模型配置和检索预算比较 Hindsight 与 Mem0；现有议题摘要加基础检索作为基线，判断复杂记忆机制是否带来实际收益。

| 样例 | 验证目标 |
| --- | --- |
| 三个议题后追问此前方案被否决的原因 | 是否找到正确依据，并引用具体材料 |
| 旧方案获批后又被正式替换，旧报告晚于新报告上传 | 是否区分发生时间、登记时间及当前有效版本 |
| 某机器人换了绑定人 | 同一机器人记忆和会话保持连续，无需迁移；新任直接可查业务历史，旧绑定不继续授予操作权 |
| 同一个人绑定两个机器人 | 是否仍按本次机器人与项目范围检索 |
| 原始资料撤回共享 | 派生记忆是否仍向无权角色泄露内容 |
| AI 把备选方案误归纳成既定方案 | 是否保持候选标识，能否追溯纠正 |
| 重复上传、更新用途、修改来源材料 | 是否正确关联版本，避免重复和错误合并 |
| 记忆服务不可用 | 能否使用已授权正式资料继续，明确缺少历史检索而不编造记忆 |

观察召回依据正确率、过期内容误用、权限检查、纠错成本，以及写入与检索的延迟和模型消耗。供应商自报评测不等于 Judex 业务效果，尤其不能将托管版本成绩当成 OSS 实测。

## 7. 第四轮答复记录

**V2-Q013：AI 自动提炼的经验能否跨议题作为待验证线索使用？** 例如“这个客户过去两次更关注交付时间”，尚未经人确认时，是只能留在原议题，还是可在有权限的新议题中作为候选经验出现？

用户答复：“允许，但标明‘AI 归纳、待验证’并附依据。它可以帮助提出问题，不能直接成为正式规则或承诺。” 已确认。这一答复不构成对某个记忆后端或自动批准能力的选择。

**V2-Q014：岗位经验默认能否跨项目复用？** 同一机器人参加新项目时，是否自动检索其所有项目的经历？

用户答复：“默认限定当前项目及已授权共享知识。通用经验经过确认和明确授权后再跨项目复用，保留来源与适用条件。” 已确认。
