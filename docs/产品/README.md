# Judex 产品主线

当前规则入口（2026-10-09）。实际工作在成员本地完成；平台保存、分析、提醒并提出建议；正式工作安排、审批和验收由有权的人确认。

身份、存储及执行架构见[详细设计](../详细设计/README.md)，原始有效答复集中在[决策答复](决策答复.md)。当前界面按项目协同与计划／任务范围讨论组织。

## 1. 产品定位与分工

Judex 是以机器人为稳定协作主体、连接成员本地 AI 工作、由人掌握正式决定的项目协同平台。

- **本地 AI 与实际工作环境**：完成开发、设计、研究等具体工作，按授权提供成果、报告和信息。平台不主动触发成员本地 AI，成员手动调用 Skill 获取事项。
- **平台 AI**：每次调用参考项目流程、节点职位关系和实际工作内容，选择获准的任职身份参与讨论，整理草稿、验收与推进建议；不以自己的判断直接取代人的任务/计划状态更新。
- **人**：可以在 Chat 提问、纠正和提供信息、证据、文件，也负责职责范围内的正式决定。
- **职位与 AI 工作身份**：用户定义职位模板，同岗可多人分别承担；新增成员可产生新任职身份，替换关联人则保留原身份的工作与记录。每份身份使用岗位职责和当前人的个人提示词，私人配置不随岗位交接。

项目首先覆盖研发和设计协作的讨论，其他内容营销、研究、客户交付、活动、采购、培训、日常运营场景用于检验通用模型；尚未承诺首版完整实现所有行业模块。

## 2. 共同概念

以下用于理解产品关系，不锁定数据库结构或技术实现。

| 概念 | 作用 |
| --- | --- |
| 项目 | 汇集目标、计划与任务、用户定义的职位模板、工作流程及资料权限 |
| 计划 | 有目标、范围和完成条件的阶段性交付；指定的负责人同时承担整体验收与状态更新；任务是详细工作拆分 |
| 任务 | 按可独立交付成果划分，最多归属一个计划，临时任务可直接归项目；当前职责交付与整项任务最终验收完成分开 |
| 职位模板 | 项目自定义的岗位职责与提示词，可从全局场景模板中选择复制，可供多人分别承担；不存在系统强制岗位 |
| 具体 AI 工作身份 | 同模板有多份持续存在的任职身份，结合各自当前关联人的个人提示词；换人不重建工作与业务记录 |
| 成员与邀请 | 管理者邀请成员时指定职位/机器人，受邀人加入后设置个人项目提示词；一人可承担多个职位，同职位也可有多位成员 |
| 工作流程 | 对话产生明确规则及其 Mermaid 图和环节说明，人工确认后同版生效；职位绑定具体流程节点，供 AI 每次调用参考和选择讨论对象、提出推进建议 |
| 议题 | 围绕问题组织讨论与结论；可以只形成结论而不产生任务，议题结束不计入交付进度 |
| 消息与材料 | 人、本地工具和平台机器人提供的原始输入，保存来源、时间和引用 |
| 提议与审批 | AI 提出的正式变化候选，以及有权人的决定；不同问题或步骤分别审批 |
| 工作与验收 | 正式安排、回传成果、按领域标准形成的验收建议和接受结果 |
| 推进与拒收 | 发送后待接收，明确接受才完成交接；各来源分别确认，接收人可选择拒收单个来源，未最终验收交付回到待完善，相关后续暂缓 |
| 业务知识与记忆 | 可按权限跨议题使用的经验与依据，区分未验证归纳和正式记录 |

计划、任务、议题分别承载阶段性交付、具体成果与讨论，正式变更经对应提案确认。任务最多归属一个计划，跨计划使用通过成果引用或依赖关联原任务，不复制工作与验收；引用方计划仍由其负责人检查整体条件。项目自定义职位及节点绑定供 AI 选择讨论对象，正式任务关联的任职身份在创建时明确，后续变更按授权确认。

开发、测试、设计等只是场景示例，不是平台固定角色。Q037 强调工作应依据用户定义的职位和流程交给相应 AI 工作身份。界面以关联人及其承担的职位为主要呈现方式；不把“显示人员”推导为业务记录随个人账号重建。

## 3. 一条完整使用路径

1. **建立项目和团队**：用户与 AI 沟通，生成明确的流程规则及其 Mermaid 图和环节说明，人工确认后同版本生效。自定义职位挂载到具体流程的具体节点；管理员邀请成员承担职位，同岗可多人，分别配置个人项目提示词。
2. **提供目标或材料**：通过 Web 或获授权的本地工具提交。原始内容先登记；在具体 Chat 中发送，记录其明确投递位置。AI 另提关联、新议题或工作安排时，需要人确认。
3. **平台内协同**：每次项目模型调用都获得项目流程参考及节点职位关系，结合新材料、实际状态和人的决定选择讨论参与者；相关输入可合并，无新信息时结束本轮等待。流程用于 AI 理解和抉择，不把调用成功或到达某节点当成正式业务状态变更。
4. **形成可审阅提议**：讨论可以只形成结论；新增或拆分工作、修改范围和分配仍先形成草稿并按权限确认。计划、任务创建时明确关联的任职身份，计划同时指定负责人。不同问题与步骤分别决定，绑定具体内容版本。
5. **作出正式决定**：Web 通过讨论中的审批卡片或“待我审批”入口操作；CLI 准备具体事项后，由浏览器审阅确认一次并执行，CLI 读取同一决定结果（2026-09-27 最新确认）。普通聊天中的赞同或反对保持讨论性质。
6. **接续本地工作与更新**：成员手动调用 Skill 获取事项，在本地完成工作后通过本人本地 AI/CLI 上报，或在界面手动更新任务。计划状态由计划负责人经同样渠道更新。工具代提交保留本人身份与来源，不凭模型推断冒充正式决定。
7. **接受成果**：区分本人当前职责交付完成与任务最终验收完成，后者满足约定验收条件后由有权人确认；同一人兼有职责时可一次明确操作完成并分别记录。计划另有一次整体验收：AI 汇总已验收任务及证据，由该计划负责人对照阶段目标和完成条件确认并更新状态，不再默认安排另一位计划验收人。议题结束不计交付进度。
8. **后续复用与变化**：经验可带依据和确认状态复用；正式变更重新形成提议。机器人持续保存业务过程，换人直接进入原 Chat 查看历史和审批。

这条路径在规则层覆盖输入、协作、决策、本地工作、成果回流和验收。有效性仍需要通过具体场景和运行实现验证。

**任务推进的补充路径**：本人上报当前职责交付 → AI 参考流程和实际内容形成推进建议 → 各发送人确认自己的交付 → AI 汇总并呈现待接收内容 → 接收人明确接受后交接完成，或选择拒收某一发送人的内容。对尚未最终验收的交付，拒收直接退回待完善，相关后续暂缓，无关任务继续。双方共享发送人、接收人和流程依据；逐来源接收与整包推进按[工作与交接合同](../plans/v1/03-工作审批与交接.md)核对。

Q050～Q053 已补齐以下异常路径：未变化且未受影响来源保留已有接收，只复核补交及确受影响部分；接收未回应到配置时限时提醒接收人和计划负责人，保持待接收，不自动同意；新版实质改变旧卡内容时重新形成建议并由发送人确认后交接；已最终验收任务可由当前有权验收的人确认重开，保留原验收记录，新范围另建任务。

依已确认规则整理的操作含义：普通接收记录完成交接，不能隐式替代来源任务的最终验收；只有对应验收职责的明确决定才能使任务最终完成。任务重开应反映在当前任务事实与提醒中，计划正式状态仍由计划负责人更新，不自动将整个计划改回进行中，也不让原验收历史消失。

当前职责交付、交接接收、最终任务验收、计划整体验收分别记录；计划负责人就是整体验收人。流程更新直接体现在后续模型提示词中，不增加逐事项切版审批。Q052 已确认旧卡不受实质影响则继续处理，受影响则重新核对改变后的交接内容，保留原记录；当前分配或交付如需正式改变，仍按已有授权处理。

## 4. AI 的协作方式

主、子 Agent 采用统一 harness 的候选实现。主 Agent 通过 `list_agent` 了解项目机器人，通过 `call_agent` 委派；子 Agent 在权限内探索，问题和结果返回主 Agent，由其选择下一步和转交内容。支持独立工作并行进行。

主 Agent 一个身份、多个议题会话；子 Agent 同议题可以续接，跨议题按需加载业务知识。共用运行机制不表示共用一份可变上下文，也不表示主 Agent 自动获得所有机器人的资料权限。

项目流程提供参与和授权边界，AI 在允许范围内选择工作方法。平台内部运行的完成、失败与超时，与人的正式审批结果分别记录。

流程是模型每次调用时获得的参考，帮助判断步骤、候选职位和推进理由。Q055 明确：用户确认为硬性要求的、可明确校验的前置或资料条件由代码检查，未满足时阻止相应推进；要放宽，须先由有权人明确调整。普通推荐路线由 AI 结合实际判断，不将每条 Mermaid 连线固定成硬顺序。材料存在不代表质量合格，质量仍由 AI 分析和人验收；平台不主动操作成员电脑。

Q049 确定后续调用直接使用新版流程提示词，Q052 确定受实质影响的在途卡片需由发送人确认改变后的内容，再交接收人处理。这两项共同成立：知识参考及时更新，人的决定继续绑定其实际审阅内容，不重新批准每个任务采用哪版流程。

## 5. 已确认的审批主规则

- 同一个问题的一次提议由指定审批位共同满足同意；不同问题和步骤分别审批。
- 第一位通过后开始倒计时，未回应者到期按规则视为同意；项目设默认时长，环节可调整，后续同意不重置。24 个自然小时仍是推荐默认值。
- 对应主管或项目创建者负责人可明确代批一个或多个未回应项，记录真实操作者及覆盖范围。
- 审批进行中任意一人退回，必须说明原因，本次提议取消；计时与其余待审批操作结束。
- 取消后可以形成修订提议，展示修改说明并重新审批，不继承旧同意或倒计时；明确不再推进的方向不自动反复重提。
- 决定绑定实际审阅内容；新材料形成修订草稿并提示变化，提交决定前核对依据和依赖。
- 本人操作、主管代批与规则超时同意保留不同来源，不能都记录成原审批人亲自点击。
- Web 普通聊天不触发正式批准或取消；CLI 正式操作使用本轮明确的浏览器一次确认机制，不接受模型自报已同意。

## 6. 当前界面入口

项目列表 → 项目协同 → 计划路线／计划或任务讨论。项目协同提供计划、需要我决定、交付与接收、共享资料。任务讨论在首次明确点击时按需建立，以后复用；上报本身不自动建立会话。

账户在右上角，项目卡提供邀请与完整设置。讨论保留中央／右侧标签、固定位置分叉、草稿和阅读位置；右栏按对象与分区去重。计划列表预览和正式路线共用全屏查看器。

具体入口见[项目协同设计](../plans/cooperation-ui/DESIGN.md)、[计划任务设计](../plans/demo4/DESIGN.md)、[聊天工作区](../界面/聊天工作区.md)。这些视图引用同一业务记录，导航、建会话和关闭标签不产生正式决定。

## 7. 机器人归属与记忆

机器人持有业务过程，绑定关系决定当前谁可以代表其职责作出操作。按这一原则，换人不迁移资料、不复制会话、不重开任务或重置审批计时；历史决定仍保留实际操作者。

Q038 已明确：新增同岗成员可产生新的任职身份，替换则修改原身份的关联人，保留业务记录与待办。界面以人员及职位展示，不改变底层身份的持续性；不能将模板、任职身份和个人账号视为同一对象。

项目成员身份、管理角色、职位模板与具体任职关系分开表达。加入由管理员邀请并指定职位/机器人，同模板可有多人；个人提示词归本人，模板定义职责，任职身份保留业务过程。管理身份、模板绑定和节点挂载本身不自动扩展业务审批权，具体操作仍按已确认授权核验。

未确认经验可以在有权限的议题中作为线索使用，标明“AI 归纳、待验证”并附依据。默认仅在当前项目及已授权共享知识范围使用；跨项目通用经验需要确认与明确授权，并保留来源和适用条件。

当前正式事实、原始材料与人的决定不依赖模型压缩摘要保存。记忆检索用于帮助找到依据，不能把一句聊天意见或 AI 归纳升级为已批准结论。
