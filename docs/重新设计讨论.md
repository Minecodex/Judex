# Judex 重新设计讨论

日期：2026-09-25。状态：V2-Q001～Q055 与后续 Q056～Q064 技术 / 身份补充已收束到 [详细设计](./详细设计/README.md)。界面演进保留在第 38 节之后，当前只有工作室 2.0 交互 Demo；正式 UI 已选择 HeroUI，视觉不必照搬 Demo。不代表真实 Agent、CLI、服务端权限或生产工作流已实现。

## 1. 用户本轮明确的方向

1. 希望做一个好的项目协同平台，机器人在其中工作，人类掌握决策。
2. 成员的具体工作主要使用各自本地的 AI 工具完成。线上 AI 承担连接、协同这些工作的作用。
3. 需要适配更多工作场景，重新审视此前偏向编码领域的设计。
4. 保留机器人作为稳定主体、人绑定机器人且可以替换的构想。
5. 参考 larksuite/cli 的 CLI + Skills 接入方式；讨论本地提交内容能否充分自由。
6. 此前设计已归档到 `history/v1`，仅是历史设想，不自动继承为本轮约束。
7. V2-Q001：允许线上 AI 自主协调，但内容应处于草稿态，经人决策后才能进入正式内容。不能把上一轮“仅重要取舍需人决策”的建议当作已经接受的规则。
8. V2-Q002：允许一个人绑定多个机器人。该答复没有一并确定单个机器人的全部任职、代理和审批规则。
9. V2-Q003：由用户手动调用（@）Skill 获取平台事项，平台不主动触发本地 AI。该边界不是仅限首版的临时方案，也不默认安排后台自动获取或后续主动触发能力。
10. V2-Q004：扩展场景讨论，包含研发、设计协作，并提出更多场景。具体首批用户和实施优先级尚未确定。
11. V2-Q005：用户提出项目创建时用文字制定流程、配置不同环节的参与机器人；提出复用 Pi 风格 harness、主 Agent 通过 `list_agent` / `call_agent` 居中调度、子 Agent 在权限内探索并支持并行的候选架构，要求结合现有实现继续讨论。具体工具契约与工程方案尚未批准。
12. V2-Q006：按议题提案确认，支持整体接受、部分接受和退回补充，提示相互依赖，避免批准后矛盾。
13. V2-Q007：按职责和授权决定；涉及其他人的工作承诺，需相应有权人或已获统筹权限的负责人决定。机器人绑定关系不扩大审批权。
14. V2-Q008：材料可以先登记，保留原文、来源和时间；正式采纳结论、接受交付、修改工作安排仍由人决定。人在确认时可以补充材料用途。
15. V2-Q009：接受文字流程经澄清和人工确认后形成参与与授权约束，工作方法保持灵活。
16. V2-Q010：主 Agent 一个身份、多个议题会话，共享项目正式内容，关联议题通过引用衔接。
17. V2-Q011：主 Agent 不自动获得全部权限，只读取获准的项目资料和可共享回复，转交时检查接收范围。
18. V2-Q012：同一议题续接子 Agent 会话，跨议题按需加载业务知识，单次探索上下文分别管理；记忆开源项目正在调研，未选择具体产品。
19. V2-Q013：未确认经验允许作为带依据的线索跨议题使用，标明“AI 归纳、待验证”，不能直接成为正式规则或承诺。
20. V2-Q014：记忆默认限定当前项目及已授权共享知识；通用经验经过确认和明确授权后再跨项目复用，保留来源与适用条件。
21. V2-Q015：允许线上主 Agent 按项目流程自动触发或续接，同时保留手动入口；连续相关材料可合并处理，无新信息或等待人决定时停止本轮运行，保留等待状态，避免重复讨论。不改变用户手动获取本地事项的边界。
22. V2-Q016：允许在项目内提交材料时不指定议题，AI 提出关联或新议题草稿，有歧义时追问用途，材料保留原权限；这些提议必须由人确认后才正式生效，明确或高置信度不能成为自动确认的例外。
23. V2-Q017：保留明确的审阅版本；新信息形成修订草稿并提示变化；人的决定绑定实际审阅内容，提交决定前检查相关依据和依赖是否变化。
24. V2-Q018：Skill/CLI 可以获取事项列表并回复同意；Web 在 Agent 讨论过程中呈现仅对应有权人可见、可操作的审批框，并有“待我审批”卡片列表，可直接同意或跳转到对应对话位置。Q021 已进一步确认本人明确同意后由 CLI 代提交直接生效，无需再到 Web 重复确认。
25. V2-Q019：区分提供意见与正式批准，AI 汇总分歧并按流程找到有权人；需要共同同意的事项在条件未满足时保持待决，规则含糊先澄清，不要求所有发表意见者都审批。共同同意的满足方式需结合本轮 Q020 的超时规则。
26. V2-Q020：待决事项对应主管或项目创建者负责人可以同意，作为兜底；多人审批同一个问题时，一人通过后开始计时，其他未回应人超时默认同意。后续 Q022 确定代批范围，Q023 确定退回取消，Q024 确定不同步骤分别审批；时间配置与推荐默认值见 Q026。
27. V2-Q021：用户看到具体事项后明确同意，本地 AI 可通过 CLI 代为提交，按本人审批直接生效，无需 Web 再次确认；获取待办不包含自主审批授权，记录本人、来源、事项与版本。
28. V2-Q022：主管或负责人可明确选择一个或多个未回应审批项代批，记录实际操作者和覆盖范围，一键处理仍清楚列出范围；不能将代批伪记为被代批人亲自操作。
29. V2-Q023：同一个问题的提议需要所有指定审批人满足同意；审批进行中任意一人退回，则本次提议取消，退回必须明确说明原因。结合 Q020，未回应仍可按既定超时规则视为同意，明确退回不适用该规则。
30. V2-Q024：不同步骤和流程分别审批；多人计时规则针对多人审批同一个问题的情况，不把多个步骤塞进同一张审批单再做局部计时。取消后的新提议不继承旧同意与计时，已由后续 Q025 确认。
31. V2-Q025：取消后的原提议保持已取消；允许根据原因形成修订提议，展示修改说明并重新审批，不继承旧同意或倒计时；原因明确要求不再推进该方向时停止，不自动反复重提。
32. V2-Q026：审批时长采用项目默认、环节可调整；从首人同意开始展示明确截止时间，后续同意不重置。用户同时保留“默认时长目前只是建议”的说明，因此 24 个自然小时记录为推荐默认值，不作为不可调整或已锁定的数值。
33. V2-Q027：AI 从文字流程整理交付约定，缺失时帮助补齐；成果回传后对照约定提出验收建议，按已有审批规则接受后才正式完成。不同领域采用各自的成果与完成标准。
34. V2-Q028：执行过程绑定机器人，人在其中作决策；更换绑定人不影响机器人既有执行过程。新绑定的人直接进入 Chat 查看历史内容与之前审批，不设置独立交接、资料迁移或接续确认流程。
35. V2-Q029：采用机器人页面聚合议题与待决事项、进入具体议题 Chat 查看讨论/成果/审批卡片的界面结构；“待我审批”可直接操作或跳回对应位置，换人仍访问原有记录。用户进一步明确 Chat 下方有输入框，人可以作为问题、信息、证据或文件提供者辅助机器人，因此人的参与不限于审批。
36. V2-Q030：普通聊天保持讨论性质，Web 正式决定通过对应审批卡片操作，聊天中的赞同或退回措辞不自动写成正式决定。CLI 保留本人明确指定事项并同意后的直接代提交能力。

37. V2-Q031：计划代表阶段性交付，有自身目标、范围和完成条件；任务是其详细需要完成的内容。
38. V2-Q032：任务按可独立交付的成果划分，同一任务可经历开发、测试、验收等环节并由不同机器人参与；有独立交付物的测试环境、测试方案等可另建任务，不按每次岗位切换拆任务。
39. V2-Q033：议题负责讨论与结论，计划、任务记录正式工作安排；议题可以只形成结论，新增或修改工作仍经提案审批，议题结束本身不计入交付进度。
40. V2-Q034：常规任务归计划，允许临时任务直接归项目。上轮建议中的“最多一个所属计划”及跨计划复用方式未被本次答复明确确认。
41. V2-Q035：保留计划整体验收。AI 汇总已验收任务及证据，对照计划目标和完成条件提出验收建议，由流程指定的有权人确认；复用任务证据，不重做各项任务验收。
42. V2-Q036：同一项目内议题与计划、任务可双向多关联；各入口查看同一份讨论和决定，不复制聊天或重复审批，正式工作变更仍经对应提案确认。
43. V2-Q037：机器人由项目自由定义，不存在平台固定的测试等业务岗位。项目可配置多个机器人/职位模板，同模板可由多位成员分别承担，各自有一份结合模板提示词和个人提示词工作的 AI 身份；界面以关联人及其职位展示。项目通过与 AI 沟通生成多张 Mermaid 流程图，计划与工作按流程流转，职位模板可选择挂载流程，代码参与硬规则校验。具体身份持续性、节点职责、流程规则来源与运行关系继续讨论；原“固定一个主责”的建议尚未得到确认。
44. V2-Q038：认同稳定任职身份。新增同岗成员产生新身份；替换关联人保留原身份的工作、会话、待办和审批历史，不增加交接审批；个人提示词仍归本人。
45. V2-Q039：明确挂载到“哪条流程的哪个节点”。结合后续补充，该绑定帮助 AI 根据当前步骤选择职位与具体 AI 身份参与讨论；不能将这一答复扩大为全部节点动作权限细节已定。
46. V2-Q040：用户通过对话制定流程，AI 生成明确规则并据此生成 Mermaid 图和环节说明；人确认后图与规则同版生效。后续补充明确流程供 AI 参考抉择，不据此推定按图边自动执行正式状态迁移。
47. V2-Q041：计划和不同类型的任务选适用流程，各自有自己的流程运行记录；多人共同推进同一份工作，各人 AI 可有独立探索会话，同岗多人不复制任务与进度。
48. Q041 后续补充：项目流程类似知识库和系统提示词的参考，每次模型调用均带入；计划与任务创建时已有分配关联机器人，成员通过本人本地 AI/CLI 或手动更新任务；计划创建时设负责人，计划状态由负责人更新。
49. Q041 后续补充：计划可组织树形任务及前置关系；前置完成后 AI 结合流程和实际内容提出推进，由完成前项的人点击同意后交给下一人。双方卡片都展示发送人、接收人和所依据流程；接收人是否还需同意未明确，不能自动套用多人审批超时默认同意。
50. V2-Q042：认同区分当前职责交付与整项任务最终完成。本人上报交付，满足约定验收条件后确认最终完成；同一人兼有交付和验收职责时可一次明确操作完成，分别留痕。
51. V2-Q043：认同两类推进：同一任务进入下一环节，前置任务完成后推进另一独立任务。卡片区分推进类型，任务树表达拆分，前置关系表达依赖，同级任务可并行。
52. V2-Q044：接收人可以拒收，因为发送人声明完成并不一定代表实际交付已满足要求；拒收可说明原因，让发送人继续完善任务。未明确正常接收是否需点击、未回应如何处理，以及拒收是否直接撤销已正式验收结果。
53. V2-Q045：计划负责人就是该计划的整体验收人，负责整体验收及计划状态更新；不采用上轮将计划负责人和整体验收人常规分开配置的建议。
54. V2-Q046：发送后进入待接收，接收人明确接受后才算交接完成。未确认将“开始处理”默认等价为接收，也未确认接收的计时和超时规则。
55. V2-Q047：尚未最终验收的交付直接退回待完善，相关后续推进暂缓，无关任务继续。对已最终验收任务的重开方式，用户未在本次答复中确认。
56. V2-Q048：各发送人确认自己的交付，AI 汇总后呈现给接收人；接收人可以选择拒收某一发送人的内容。其它来源的接收状态是否保留、补交复核范围等仍待细化。
57. V2-Q049：按照新版流程推进，提示词直接修改；后续调用直接采用新版参考，不再要求每个已有计划/任务另行批准切换。该答复不等于允许抹掉实际发生的历史决定，已发出未接收卡片如何处理仍待细化。
58. V2-Q050：认同未变化且未受补交影响的已接收来源保留结果，仅核对补交部分；确有影响的其它内容由 AI 指出并交相关人复核，不整包清空接收意见。
59. V2-Q051：认同项目可配置接收提醒时限，到期提醒接收人和计划负责人，保持待接收，由负责人协调或按权限安排改派，不自动记为原接收人同意。
60. V2-Q052：认同新版没有实质影响的卡片继续处理；实质改变接收人或交付要求时，AI 更新建议、发送人确认改变后的内容，再交接收人处理，原记录保留。这是交接内容的确认，不是逐事项审批切版。
61. V2-Q053：认同当前有权验收的人可确认重新打开已最终验收任务；保留上一轮验收记录，修正与复核作为新一轮。超出原约定范围的新需求另建任务。
62. V2-Q054：认同一个任务最多归属一个计划，临时任务可直接归项目；其他计划通过成果引用或依赖共用原任务与验收记录，不复制工作。引用方计划仍由自己的负责人判断整体验收条件。
63. V2-Q055：认同明确确认为硬性要求的、可明确校验的业务条件由代码检查。普通推荐路线由 AI 结合实际判断；放宽硬要求由有权人明确调整。代码核对记录与材料等客观条件，成果质量仍由 AI 分析和人验收。

除以上方向及后文明确标记的用户答复外，其余均为建议或待讨论内容。尤其不自动继承原来的 Git 规则、任务状态、审批层级、目录结构、数据库与沙箱选择。

## 2. 候选产品定位

建议将 Judex 定位为：**以机器人为组织成员、围绕目标开展协作、由人掌握关键决策的 AI 协同工作空间。**

用户获得的价值是：自己的本地 AI 能持续接上团队正在做的事，并把成果交到需要它的人或机器人手中；团队可以减少反复传递背景、核对口径、追问依赖和整理决策材料的工作。

需要验证的产品假设：线上 AI 能否有效完成跨成员的理解、协调与综合，比仅提供共享聊天、文件和任务列表更有价值。此处不宣称市场独创性，也不把“机器人互相聊天”本身当作产品价值。

## 3. 机器人、人、本地 AI 的关系

建议把四个概念分开：

| 概念 | 承担什么 |
| --- | --- |
| 职位模板 | 用户在项目中定义的职责、提示词与参与要求，同模板可由多位成员承担；岗位名称任意，研究、设计、销售、开发只是示例 |
| 具体 AI 工作身份 | 同一职位模板有多份稳定任职身份；新增成员可增加身份，更换其中一个身份的关联人保留其工作与记录，Q038 已确认 |
| 当前绑定的人 | 在机器人当前职责与授权范围内决策，也可在议题中提问和提供资料；更换绑定不搬迁或重建机器人的工作 |
| 本地 AI 会话或工具 | 当前执行工作的入口，可更换模型、工具、电脑或会话，不等于机器人的永久身份 |

Q037 已明确同一职位模板可由多位成员承担，并有各自的 AI 工作身份。模板职责与个人偏好组合；具体工作的分派范围、谁被调用或参与审批仍需由项目流程和授权确定，不能把同模板自动解释为全部人都参加或共享全部上下文。

已确认一个人可以绑定多个机器人。建议每个机器人在任一时刻都有明确的主责人；不同机器人即使共享同一个人，也不应冒充两份独立的人类审核意见。后两项仍属建议。

线上机器人整理协作背景，本地 AI 获取获准的工作上下文、完成本地工作并返回成果，平台内的业务执行过程归机器人。Q028 已明确换人改变当前代表机器人决策的人，新成员直接查看该机器人 Chat 历史与已有审批，不增加交接流程。Q029 又明确人可以在 Chat 直接提问、补充信息、证据或文件；这不会把机器人的执行上下文、资料和审批进度转移到个人账号。

据此，审批位应关联机器人及其流程职责，由当前有权的绑定人操作；每次实际决定同时保留操作者身份和时间。更换绑定本身不重置任务、审批状态或已有截止时间，也不改写前任已作出的决定。原成员不再凭旧绑定操作，但如仍有独立的主管等权限，按该权限核验。这是机器人持续归属原则的实现含义，不是新的交接审批步骤。

个人设置和凭据与机器人业务记录仍需区分，Q028 不把任意私人账号内容定义为机器人业务资料；已有项目与资料访问边界继续有效。

## 4. 线上 AI 应承担的工作

线上 AI 的产出应能推动协作：

- 理解目标和现有材料，提出可执行的工作拆分与完成标准。
- 找到适合承担事项的机器人，协调责任、输入输出与依赖。
- 收到成果后判断它回答了哪些问题、缺少什么、谁还需要知道。
- 核对不同成员的成果，发现冲突的假设、相互等待和范围变化。
- 汇总已有结论，形成团队可复用的工作背景。
- 把无法自行消解的分歧整理为决策材料，给出选项、依据和影响。
- 把人的决定传播到受影响的事项和机器人，明确哪些工作需要重做或补充。

已确认：AI 自主协调产生的内容先处于草稿态，经人决策后才能进入正式内容。正式目标、分工、承诺和结论不能仅因 AI 达成共识就自动生效。提案确认粒度和授权原则见 V2-Q006、Q007。V2-Q005 提出的信息流是按项目文字流程由主 Agent 居中选择参与者和转交内容，具体执行边界继续讨论。

平台收到“请帮我买下这个服务”之类文字，不应仅凭内容就视为采购授权。自由表达、身份权限和行动授权是不同层面的设计。

## 5. 通用协作核心与领域能力

建议先围绕少量共同概念设计，而不是把软件研发状态改名后推广到所有行业。

| 通用概念 | 含义 | 软件工作示例 | 非软件工作示例 |
| --- | --- | --- | --- |
| 目标或工作主题 | 为什么开展这项协作 | 完成交付版本 | 准备品牌活动、完成客户方案 |
| 事项与责任 | 下一步要解决什么、谁负责、等待什么 | 修复登录故障 | 核实报价、补充访谈、完成视觉稿 |
| 工作贡献与成果 | 带来源的观察、材料、分析或交付物 | 代码引用、测试报告 | 访谈笔记、表格、图片、方案文件 |
| 决策 | 谁基于什么选择了什么，并影响哪些工作 | 接受延期、批准发布 | 选择主题、批准预算、接受交付 |
| 协作背景 | 已形成的目标、约束、术语、事实与待解问题 | 接口约定、环境说明 | 品牌要求、客户限制、研究假设 |

此前曾建议项目支持长期职责、周期性工作和临时咨询，并考虑不强制所有事项先挂到“项目→计划→任务”树中；该建议不等于用户确认取消计划和任务。Q031～Q033 已明确保留其业务分工；是否允许独立任务等层级例外继续讨论。

领域能力通过技能与协作模板补充。例如研发模板理解仓库、分支和 Bug；营销模板理解受众、品牌材料和渠道；研究模板理解资料来源、假设和证据。这些属于可插入的领域语义，不要求每个空间都配置。

Q027 已确认完成条件由 AI 从文字流程整理、缺失时帮助补齐。设计可验收具体稿件，研究可验收结论和依据，各领域采用自己的标准；成果回传后 AI 提供对照与验收建议，按已有审批规则接受后才正式完成。

## 6. 自由提交与可靠协作

建议允许本地 AI 自由提交文字、附件、链接、表格、图像及混合材料。文件格式不支持直接分析时仍可保存，并明确分析局限，不把“已上传”当作“已理解”。

大部分关联、摘要与分类交给 AI，常规上报不要求用户先填一套领域专用表单。但传输仍需最小上下文：身份与授权范围、所属工作空间、提交时间、来源、原始内容，以及可选的关联对象和提交意图。身份和权限由认证决定，不信任自由文本中的自我声明。

建议区分：

1. **原始贡献**：成员实际提交的内容及来源，保留原文和更正历史。
2. **AI 理解**：摘要、关联、冲突、疑问与建议，能够追溯依据和被纠正。
3. **业务决定**：经有权的人决策后进入正式内容的承诺或结论。

同一份材料可能服务多个事项。机器人可提出关联；有歧义时只追问关键缺口，不要求成员重新填写整套材料。AI 抽取的状态不应在未区分事实、推断和决定时直接成为团队共识。

V2-Q016 已明确：AI 对材料归属、关联议题或新建议题提出的建议都要人确认。材料登记可以先完成，正式关联仍待确认，不能因关联判断明确就直接生效。

Q029 的议题输入框提供了用户直接选择投递位置的入口。人在当前议题中发送消息/附件时，系统可按其明确选择记录到该 Chat，属于原始材料登记，不需要 AI 再次猜测投递位置。AI 另行提出跨议题关联、新建工作或将内容用作正式结论时，仍按 Q016、Q008 处理，不能把“收到附件”解释为正式采纳。

CLI 重试不应重复制造事项；上传时应能携带稳定的提交标识。大文件、权限和来源追溯需要工程约束，但不以固定报告章节限制表达。具体接口待产品模型确定后设计。

V2-Q008 已确认原始材料可先登记，确认时可以补充用途。建议把用途说明作为关联材料的单独记录，例如“仅供参考”“用于回答客户提出的问题”“作为本次交付候选”；保留说明者与时间，原始文件不被改写。示例用途不是强制枚举，也不要求上传时填写完成。用途发生变化后，相关 AI 理解与草稿是否需要更新，应可追溯。

## 7. 一条非编码协作示例

示例仅用于验证建议，不代表已批准的业务流程。

1. 人提出目标：“两周内完成新产品线上发布活动方案”，并给出已知限制。
2. 线上主 Agent 按项目文字流程组织相关机器人，形成研究、内容、视觉和渠道准备事项草稿；按职责与授权由有权人决定后形成正式安排。
3. 成员在本地手动调用 Skill，获取当前目标、已经作出的决定、应交付内容和相关依据。仅打开本地 AI 不代表自动获取。
4. 研究成员提交访谈笔记与表格，设计成员提交图片，渠道成员提交报价和排期，各自保留适合工作的表达方式。
5. 线上机器人发现设计方案假定的受众与研究结果不一致，而且渠道排期可能影响目标日期。
6. 子 Agent 将意见与问题返回主 Agent，由其按流程安排后续协同并形成议题提案，向有权人呈现选项、证据和受影响的工作。这里采用用户提出的中心调度方向，具体实现另见架构讨论。
7. 负责人选择方案；决定关联到已有材料，在平台上更新获准生效的内容。成员下一次手动调用 Skill 时获取相关更新，再让本地 AI 接续修改。
8. 根据事先约定的交付标准，由相应负责人确认成果；之后的执行反馈可开启新的协作事项。

需要闭合的链路：目标草稿→人的决定→正式责任→用户手动获取→本地工作→成果登记→理解与协调草稿→人的决定→下一次手动获取。确认时可补充材料用途，不能把材料登记等同于内容已被采纳。

更正、冲突、离线、等待外部答复和责任人更换都应可表达。状态展示必须区分“已发出”“对方已接收”和“已完成”，避免把消息投递当成实际进展。

## 8. CLI + Skills 的借鉴方向

从 [larksuite/cli 官方仓库](https://github.com/larksuite/cli)可借鉴：面向工作意图的快捷操作、可发现的命令结构与机器可读输出，以及通用技能和领域技能的分层。接入工具与领域工作指导可以分别演进。

Judex 候选接入层次：

- **API** 提供稳定的业务能力与身份、权限和行为记录。
- **CLI** 让本地 AI 取得背景、检查待处理事项、提交贡献、查看决定及回报结果。
- **Skills** 指导本地 AI 何时同步、如何使用背景和表达意图，领域技能再补充本行业方法。

必须双向连接。本地 AI 除了上传，还要能够拿到新的决定、待回答问题和最新上下文。

已确认：用户在本地手动调用 Skill 获取事项，类似主动打开邮件。平台保存待处理内容，等待用户获取；平台不主动触发本地 AI，也不因本地 AI 启动就自动获取。这是当前产品边界，取消上一轮对持续订阅或本地执行连接器的路线建议。

此前调研的官方 [事件 Skill](https://github.com/larksuite/cli/blob/main/skills/lark-event/SKILL.md)提供事件消费与本地事件总线；此项仅为参考事实，不纳入 Judex 当前本地接入方案。

官方 [身份与权限说明](https://github.com/larksuite/cli/blob/main/skills/lark-shared/references/lark-shared-identity-and-permissions.md)区分用户与应用身份。对 Judex 的启发是显式记录“代表哪个机器人、由哪个人或工具操作、采用什么授权”，而不是直接照搬其身份模型。

共享背景应按当前任务与权限提供，并附相关材料引用；不宜每次传递整个项目历史。过期背景和重要决定变化要能被本地 AI 察觉。

建议每次手动获取提供“自上次获取后的变化”，并带上资料版本和时间。平台可在接收成果时检查其依据是否已经变化，形成提示或协调草稿，不能假设成员一直持有最新背景。获取信息、承诺接手和完成工作应分别表达；多机器人绑定时，本次代表哪个机器人也需明确。这些交互仍待进一步设计。

## 9. 界面与体验建议

主要体验围绕三个入口组织：

- **需要我判断**：决策问题、推荐、其他选项、依据、影响范围，支持追问、修改与决定。
- **正在协作**：目标、负责的机器人、当前成果、等待和分歧，以及下一步。
- **我的机器人**：职责、进行中的事项、本地接入、工作记忆、Chat 历史、审批记录及当前绑定；换人不出现额外交接流程。

机器人之间的完整消息可展开查看，但默认呈现事实变化、当前结论和待解问题，避免大量自动聊天淹没有效信息。

决策材料应关联当时的具体成果版本。后续材料出现重要变化时，提示原决定是否需要复议，而不是让新文件悄悄替换原审批依据。AI 误解、分错对象或漏掉事实时，应能直接纠正，并看到哪些摘要和事项受影响。

不预先固定每次动作必须由多少个模型实例讨论。职责隔离与记录归属是产品语义，实际模型调度可以按需要进行；无止境的机器人对话既增加成本，也不等于达成协作。

一次协调应有明确的待解问题、输出要求和停止条件。若没有新增依据仍无法达成结论，平台应汇总分歧交给人处理，而不是继续生成相互附和的对话。

首次使用可从自然语言目标和已有文件开始，由 AI 提议工作组织方式。不同领域的模板帮助启动，用户可以修改，不把配置流程作为开始工作的前置负担。

Q029 已确认 Web 议题 Chat 下方提供输入框，人可直接提问、补充信息、证据和文件，辅助机器人。团队可以逐步接入本地 AI；没有使用 CLI 的协作者也能在 Web 提供信息。

## 10. 首轮验证与边界

用户要求扩大场景覆盖，研发与设计协作已被点名。本轮以第 13 节的九类场景检验同一协作核心；具体首批团队、验证顺序和实现范围仍待决定，不把上一轮“两类场景”的建议当作用户选择。

建议优先跑通：机器人身份与责任、用户手动获取背景、提交成果、跨成员综合草稿、一次人类决策及其在下一次获取时的传递。平台不主动触发本地 AI；不预设全面自动化执行平台或完整流程编排器。

验证时关注：为接续工作需要手工补多少背景；一次决定是否准确传到受影响者；AI 误解能否低成本纠正；需要人工维护多少台账；同一套机制能否承载第二领域。机器人发言数量和自动创建任务数量不应成为成功指标。

## 11. 第一轮答复记录

**V2-Q001：线上机器人的主动权。** 原问题提出在职责范围内自动协调、遇到关键取舍再交给人的建议。

用户答复：“可以，但是应该是作为草稿态，要人决策之后才能进入正式的内容”。

记录结果：接受自主形成草稿，正式化必须经过人的决定。不能保留“普通内部协调可自动正式生效”的解释。

**V2-Q002：人和机器人的绑定。** 原问题讨论一人可否负责多个机器人及其责任模型。

用户答复：“允许一个人绑定多个”。

记录结果：确认一人可绑定多个机器人，其他任职、代理和独立审批建议尚未由该答复确定。

**V2-Q003：本地 AI 如何接续工作。** 原问题区分按需接入和平台主动触发。

用户答复：“平台事项要用户手动@skill来获取才行，平台不应该主动触发本地AI，就像邮件一样用户自己点击才查看”。

记录结果：本地获取由用户显式发起，主动触发不属于当前产品方向，不保留为默认后续路线。该答复针对获取方式，未确定每次上传是否需要另一次手动调用。

**V2-Q004：先服务哪一类团队。** 原建议先选两类真实工作验证。

用户答复：“最好多搞几个场景，研发，设计协作 ，你再多提几个”。

记录结果：扩展场景讨论；明确包含研发、设计协作；其他场景由本轮提出，实施优先级尚未选定。

## 12. 草稿与正式内容的候选协作机制

本节同步 V2-Q005～Q008 答复；其中已确认的提案粒度、授权和材料登记原则与仍待讨论的工程建议分别表述。

建议平台同时呈现“当前正式内容”和“正在讨论的草稿”。AI 可以起草新的事项与变更，但已生效内容维持原决定，直到有人批准相应修改。

用户提出在项目文字流程中配置环节参与者，由主 Agent 选择调用机器人及转交内容，子 Agent 的问题和结果先回到主 Agent。不能将原建议解释为所有机器人自由互传消息。建议每次转交保留草稿标识和来源，避免被理解为正式任务、已承诺日期或已批准结论。草稿可见性和正式生效是两个独立问题。

已确认按议题提案作出决定，支持整体接受、部分接受、退回补充及依赖提示。建议提案说明：要决定什么、当前正式内容是什么、拟改成什么、影响哪些事项和机器人、依据哪些具体版本的材料。若部分内容互相依赖，应说明影响，不能形成矛盾的正式结果。

例如活动方案先形成正式安排；后续新增报价导致排期变更建议，则呈现原安排与新草稿的差异。按 Q024，不同问题和步骤分别提交审批，议题层面的部分接受通过选择不同审批事项表达；同一个问题中的同意针对同一份提议。若决定所依据的正式内容或材料已经变化，应提醒复核。

已确认授权原则：人确认其权限内的内容，涉及其他负责范围的承诺时，需要相应有权人决策，或由已有明确授权的负责人统筹。机器人绑定关系本身不扩大审批权；多人同意、主管代批、超时与退回规则已由 Q019～Q026 细化，具体身份与权限实现仍需设计。

已确认原始材料可以先登记并保留原文、来源、时间；确认时可以补充材料用途。任何技术上的上传成功、信息获取成功，都不能替代对内容或工作责任的正式接受。

## 13. 跨场景验证建议

以下九类用于检验同一协作核心，除研发和设计协作外均为新建议；不是九套已经确定的行业模块。

| 场景 | 本地工作与提交 | 平台 AI 草稿协同 | 人决定什么 | 对共同模型的检验 |
| --- | --- | --- | --- | --- |
| 研发交付 | 实现、分析、代码引用、测试与部署报告 | 需求和成果关联、依赖与问题归纳、交付方案 | 范围、分工、变更与交付接受 | 多角色依赖与跨版本依据 |

## 15. 协同闭环与第五轮确认

本节已同步 V2-Q015～Q017。明确标记的原则已获确认，补充交互和实现细节仍为建议。记忆后端、具体运行框架和 Demo 均未因此选定或实现。

已确认的核心机制可以连接为：材料登记→平台按流程协调草稿（含必要的关联或新议题建议）→形成议题提案→有权人决定→批准范围内的正式内容生效→成员手动获取→本地工作与新的材料回流。关联建议本身需要人的确认，不能由 AI 自行跨过这一环。

### 平台内协同的启动与续接

V2-Q015 已确认按项目流程自动触发，同时保留手动入口；连续提交的相关材料可以合并处理。无新信息或正在等待人决定时，保存现场并停止本轮运行，等待后续事件，不反复生成相同结论。具体事件配置、合并时机和去重机制仍待实现设计。

这里只讨论线上主 Agent 的运行时机。用户手动调用 Skill 才获取事项的本地边界已经确定，不重新讨论或改变。自动启动平台分析也不等于正式内容自动改变。

### 自由提交后的材料归属

V2-Q016 已确认提交者可以指定项目与议题，也可以在已选项目中只提供材料。未指定议题时，AI 先提出与已有议题的关联或新议题草稿；有多种合理解释时追问关键用途。用户特别补充，这些提议都要人确认，不因 AI 判断明确而直接形成正式归属。

材料原有可见范围保持有效。提出或确认关联都不能隐式扩大可见范围；无法确定关联时，建议先保留为项目内待整理材料，不阻塞登记。

### 提案、部分批准与新材料

V2-Q017 已确认人作决定时面对明确版本的提案，AI 收到新信息可以生成修订草稿并提示变化，不能静默覆盖审阅内容；人的决定绑定实际审阅的内容，提交决定前检查依据和依赖是否变化。具体版本标识、变更展示和冲突处理机制仍待设计。

按 Q024，“采用视觉方案 A”和“追加某项资源”若是不同问题或流程步骤，应形成各自独立的审批事项。议题可以集中展示它们，但不在同一问题的审批单内拆出局部计时。若方案 A 必须依赖新增资源，仍需明确展示并核对依赖，避免独立审批后形成矛盾安排。

新材料影响待决内容时，提示相关变化并生成修订草稿；已正式生效的结论不会仅凭 AI 推断自动撤销。如需改变，另行形成由有权人处理的变更提案。

## 17. 人的决策入口与第六轮确认

本节同步 V2-Q018～Q020。用户明确改变了上一轮仅 Web 审批、无超时同意的建议；最新答复优先。原 V1 的固定层级仍不自动继承，本轮主管兜底与超时同意来自新的明确答复。

### 确认入口

Q018、Q021 已确认 Skill/CLI 获取列表后，用户明确同意具体事项，本地 AI 可代提交直接完成本人审批，无需 Web 重复操作。入口开放不代表本地 AI 可以自行审批一切事项；具体身份和授权实现仍需设计。

Web 已确认两种入口：Agent 讨论位置中的审批框，以及“待我审批”卡片列表；卡片可直接同意，也可跳转到对应对话位置。审批框仅向对应有权人显示并允许其操作。其他成员能看到哪些审批进度或结论，继续受相关内容权限约束，未由本答复统一公开。

为了减少重复操作，同一议题下的关联建议、用途说明和业务提案可以集中呈现，每一项清楚标明变化、依赖及谁有权确认。集中呈现不等于一并批准；需要的确认仍逐项明确记录。是否一次提交多个决定，应根据各项权限和流程允许范围设计，不能跨过材料关联的确认要求。

### 多人参与与意见冲突

Q019 已确认在项目文字流程中区分提供意见的参与者与正式批准者。AI 整理意见和分歧，按流程找到有权人；无需每个发表意见的人都参与最终审批。

对同一个问题，流程明确指定审批人；Q023 要求所有指定审批人满足同意。Q020 允许未回应人按超时规则视为同意，Q022 允许主管明确代批，记录应保留不同来源。任意一位审批人在进行中退回并说明原因，本次提议即取消，不能再到期通过。主 Agent 自行达成共识仍不等于满足审批条件。

### 无人处理与人员暂缺

Q020、Q022 已明确待决事项对应主管或项目创建者负责人可以选择一个或多个未回应审批项代批，操作记录体现实际操作者与覆盖范围。Q023 的取消结论不通过继续代批剩余项来绕过。

多人审批同一个问题时，一人通过后开始计时，其他未回应人超时默认同意；不同步骤独立审批。Q025 已确认取消后修订重提不继承旧同意与计时；Q026 已记录项目默认、环节可调及后续同意不重置，24 个自然小时仍为推荐默认值。该机制在平台运行，不触发成员本地 AI。

## 19. 多入口审批与第七轮确认

本节已同步 Q021～Q026：CLI 本人指示后直接审批、明确范围的主管代批、任意一人退回则取消且必填原因、不同步骤分别审批、取消后重提及计时配置。具体运行实现仍标记为建议，24 小时作为推荐默认值。

### 统一审批内容与入口

建议讨论中的审批框、“待我审批”卡片和 CLI 列表引用同一审批事项与提案版本。卡片与 CLI 输出展示具体待决内容、变化、影响、当前审批状态及相关截止时间；快捷同意不强制要求再跳回讨论页重复操作。

讨论位置跳转应定位对应版本的审批内容，内容有权限才允许读取；审批按钮只对有权人可见，实际提交仍由服务端校验身份、权限与版本。重复点击或 CLI 重试不应重复批准、重复生效或重新启动计时。

### CLI 的本人指示

Q021 已确认：本地 AI 展示具体事项后，用户明确同意，本地 AI 通过 CLI 代为提交，按本人身份记录并标明来源、事项与版本，不再要求另到 Web 重复同意。概括性的“看看我的待办”不包含审批指示。明确多个独立事项时，可以分别记录对各项的同意，不能无说明扩展范围。

普通 API 凭据只证明调用身份和权限，不能单独证明本轮有人亲自看过内容。具体采用本地显式交互、一次性授权或其他方式，需要后续定义；不把 AI 自行填写的“human_confirmed”字段宣称为可靠的真人确认凭证。无需在本轮选定实现方式。

### 同意的来源与主管兜底

建议记录本人通过 Web/CLI 主动同意、主管或负责人代批、系统按规则超时视为同意等不同来源。记录实际操作者、被处理的审批范围、提案版本和采用的规则，不能将超时或代批写成原审批人亲自点了同意。

Q022 已确认主管兜底可明确选择一个或多个尚未回应的审批项代批，并记录真实操作者和范围。Q023 已确认一人退回即取消，因此代批不覆盖已退回，也不能使已取消提议复活。人员具有多个机器人身份时，建议同时保留实际人物与所代表职责，不制造多个独立真人操作记录。

### 超时的对象与版本

Q023 已确认审批进行中任意一人退回，本次提议取消，且必须明确说明原因。这比上一轮“继续保留分歧待处理”的建议更明确。取消后结束该审批的计时，关闭剩余待审批操作；超时不能继续将其推成通过。

Q024 已明确计时针对同一个问题的多人审批。不同步骤、不同问题各自形成审批事项，不共享首个同意或倒计时；取消后重提与计时配置以 Q025、Q026 为准。

Q026 已记录同一审批轮次从首人同意开始显示明确截止时间，后续同意不重置倒计时；项目设默认时长，环节可以调整。24 个自然小时保留为推荐默认值。重复请求不能改变已发生的首个同意时间，具体去重和截止检查属于实现细节。

Q025 已确认取消后的原提议保持已取消，修订提议展示修改说明并重新审批，不继承旧同意或倒计时；明确不再推进该方向时停止，不反复重提。新一轮仍按首人同意启动计时。对于尚未取消、仍有效的审批期间另起草稿，建议不静默废弃旧审批；适用性与依据变化继续按 Q017 检查。

示例：A 同意、B 填写原因退回、C 没回复。按 Q023，本次提议立即取消，C 不再需要回应，也不会在截止时间被追加为超时同意。A 的历史同意与 B 的退回原因保留；其他独立问题的审批不因这张单取消而被统一取消。

超时可由普通后台计时任务按规则处理，无需主 Agent 持续运行或反复询问模型。处理时重新核对版本与实际审批状态，保留来源，避免已处理、已撤回或已变更事项重复生效。具体并发、截止边界与故障恢复在规则确认后设计。

## 20. 第七轮答复记录

**V2-Q021：CLI 回复同意怎样成为正式审批？** 是否采用“用户看到具体事项后明确同意，本地 AI 通过 CLI 代提交，直接按本人审批生效”的方式，无需再到 Web 重复确认？

## 21. 当前审批模型

为便于界面与实现统一，建议把同一个问题的一次提议称为一张审批单，多个步骤或问题各有自己的审批单；一个议题可关联多张单及其依赖。该命名不增加新的业务审批层级。

| 当前审批单发生的事件 | 结果 |
| --- | --- |
| 尚无人通过 | 等待首次同意；没有因“首人同意”启动的倒计时 |
| 第一人同意，尚有人未回应 | 开始计时，继续等待同一问题的其他审批人 |
| 所有指定审批位满足同意 | 本次提议通过；同意来源保留本人、代批或规则触发的区别 |
| 到期且审批仍有效、没有退回 | 未回应位按 Q020 视为同意，满足条件后通过 |
| 审批进行中任何一人退回并说明原因 | 本次提议取消，停止计时和其他待审批操作，保留历史与原因 |

“退回导致取消”与“缺少材料暂时等待”是不同事件；不能把讨论里提出问题自动视为退回，正式退回由有权人在审批入口明确提交。

建议 Web 和 CLI 的退回操作都要求填写原因，由服务端校验。取消与到期通过需要一致的状态检查，避免重复任务或并发操作使同一审批同时出现通过和取消。已生效的其他独立事项不自动撤销；涉及依赖变更时继续遵循正式变更流程。

### 输入后的处理

- 普通问题：主 Agent 根据当前议题回答，必要时按流程通过 `call_agent` 获取相关机器人的分析。
- 补充信息或纠正：保留原消息，更新本轮讨论依据和草稿；若影响正式安排，提出相应变更提议。

- 工作指示：可以引导允许范围内的分析，如“请对照这两份稿件”；正式分工、范围和成果接受仍按既有决策规则处理。
